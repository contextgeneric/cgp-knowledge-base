# CGP v0.7.0

The ergonomics release, and the most recent shipped version. It introduces the attribute suite that
defines how CGP is written today (`#[cgp_fn]`, `#[implicit]`, `#[uses]`, `#[extend]`,
`#[use_provider]`, `#[use_type]`) and removes `#[cgp_context]`, the last of the scaffolding that made
a CGP context look unlike a struct.

- **Tag**: [`v0.7.0`](https://github.com/contextgeneric/cgp/releases/tag/v0.7.0), 28 February 2026
- **Announcement**: [Supercharge Rust functions with implicit arguments using CGP v0.7.0](https://contextgeneric.dev/blog/v0.7.0-release),
  documented at [website/blog/v0-7-0-release.md](../website/blog/v0-7-0-release.md)
- **Release notes**: the website's
  [cgp v0.7.0 release notes](https://contextgeneric.dev/docs/release-notes/cgp/v0.7.0), written from
  the source diff since [v0.6.1](v0-6-1.md), beside this document, the old changelog entry, the GitHub
  Release, and the post. The old entry is the topmost in
  [CHANGELOG.md](https://github.com/contextgeneric/cgp/blob/main/CHANGELOG.md), but **headed
  "v0.6.2 (2026-03-01)"**: the release was renumbered to v0.7.0 once its breaking changes were
  counted, and the heading was never corrected. Read it as v0.7.0.
- **Relation to today**: the closest release to current. Its features are unchanged in v0.8.0 apart
  from one separator character.

## What it introduced

**`#[cgp_fn]` with `#[implicit]` arguments** turns a plain function into a context-generic trait
whose marked arguments are fetched from the calling context's fields rather than passed by the caller.
A struct opts in with `#[derive(HasField)]` and nothing else. This is the lowest-ceremony entry point
CGP has ever had, and it is what the site's tutorials now teach first.

**Four attributes replace hand-written bounds.** `#[uses]` imports another CGP trait so a
function or provider can call it on `self` without knowing its requirements; `#[extend]` does the same
while re-exporting it, which the announcement frames as the `pub use` to `#[uses]`'s `use`;
`#[use_provider]` fills in the stray `Self` argument on an inner provider's bound, so a higher-order
provider's dependency reads like an ordinary one; and `#[use_type]` imports an abstract associated
type as a bare alias, removing `Self::` from every use site, and its equality form
(`#[use_type(HasErrorType::{Error = AppError})]`) pins an abstract type to a concrete one.
`#[implicit]` also becomes available inside `#[cgp_impl]`, which removes the getter-trait layer from
provider implementations entirely.

The announcement pairs these with a section answering the objection the word "implicit" invites.
Against Scala's implicit parameters, it argues three differences: resolution scope, since CGP resolves
only from a field on `self` rather than from a layered implicit scope; unambiguity, since CGP matches
on *name and type* where Scala matches on type alone, and Rust forbids duplicate field names; and
transparency, since every `#[implicit]` expands mechanically into a `HasField` bound and a `get_field`
call.

## What it changed or removed

**`#[cgp_context]` is removed**, following its deprecation in [v0.6.0](v0-6-0.md). A context is now an
ordinary struct with a `delegate_components!` block, and the `{Context}Components` provider struct no
longer exists.

**The consumer-trait blanket impl is simplified** to `Context: Greeter<Context>`, dropping the
`DelegateComponent` lookup because the provider trait's own blanket impl already performs it. A probe
against `cgp` 0.6.1 and 0.7.0 from crates.io found no code that compiled before and fails now. A
context that `delegate_components!` wires satisfies both forms, and the one new case is a context that
implements the provider trait for itself by hand, which now implements the consumer trait too. The
announcement presents the ambiguity of a static call such as `App::make()` as a consequence of this
change, but the same call already fails with `E0034` at 0.6.0 and 0.6.1, since a context wired by
`delegate_components!` is its own provider there as well. The release notes list the change under
their improvements for this reason.

**`check_components!` and `delegate_and_check_components!` change syntax.** The `Name for Context`
form is replaced by a bare context name with an optional `#[check_trait(...)]` attribute, and
`delegate_and_check_components!` gains `#[check_params]` and `#[skip_check]`. With no attribute the
macros generate `__Check{Context}` and `__CanUse{Context}` as the trait names, which the changelog's
"change the default check trait name" entry (#215) describes: v0.6.1 had no default, since the name was
required. The fused macro also drops its separate table type: `CanUseApp for App; AppTable { … }` has
no replacement in it, and a table other than the context is wired with `delegate_components!` and
checked with `check_components!`. The changelog and the announcement omit that last change, and a
probe confirms it: the old fused form with a hand-written table compiles at 0.6.1 and fails at 0.7.0.

**Owned getter and implicit values are announced as requiring `Copy` rather than `Clone`**, so that
an expensive value is never silently cloned into an owned argument. The published crate does not
enforce it: the change renamed the macro's internal field mode to `Copy`, but the generated code
still calls `.clone()` with no `Copy` bound, so an owned `String` compiles as an `#[implicit]`
argument or a getter return against `cgp` 0.7.0.

**Two names go.** The `{Type}Of` alias is dropped from `#[cgp_type]`, superseded by `#[use_type]`, and
`ProvideType`/`TypeComponent` are renamed `TypeProvider`/`TypeProviderComponent` to match the
convention `#[cgp_type]` established. `ErrorOf` and `RuntimeOf`, which `#[cgp_type]` used to generate
for `HasErrorType` and `HasRuntimeType`, stay as hand-written aliases, and a probe finds both at both
releases.

One bug fix: `#[cgp_type]` when an associated type carries a self-referential bound.

## The changes the release notes leave out

**The old changelog and GitHub Release have slips.** Both link pull requests 200, 211, and 213 as
`pull/#N`, which is not a pull-request path, and the changelog heads the entry v0.6.2. They list the
`Copy` change as breaking, though owned values still need only `Clone`, and omit the removal of the fused check macro's
table type and the `#[check_trait]` names.

**The announcement leaves out part of the attribute suite.** `#[extend_where(...)]` puts a predicate on
the `where` clauses of the generated trait and impl, `#[use_type]` takes an `as` alias and a foreign
form `@Context::Trait::Type`, `#[extend]` and `#[use_type]` work in the getter macros, and
`#[cgp_impl(Self)]` writes a consumer-trait impl for one concrete context (#206). The notes list each.
Probes against `cgp` 0.6.1 and 0.7.0 from crates.io confirmed that each feature compiles at 0.7.0 and
fails at 0.6.1, and that a `&str` implicit argument needs a `String` field, which v0.8.0 relaxed.

**Names and syntax used and discarded during development.** `#[use_provider]` first separated its
bounds with `,` and changed to `+` before the tag (#207), and the spans of abstract type identifiers
were fixed within the release (#199). Neither shipped in its earlier form.

**The macro implementation was reorganized.** `cgp-macro-lib` gained a `cgp_fn` module and a
`cgp_impl` module, `to_camel_case_str` moved to `cgp_macro_lib::utils` so `cgp-extra-macro-lib` depends
on the library, and the `#[cgp_context]` derivation and its specification type were deleted. The
`pub use` lists of `cgp-extra`, `cgp-field`, and `cgp-type` were reformatted or renamed with no change
to what they export beyond the type provider names. The workspace crates moved to 0.7.0 in the release
commit (#209). None of it changes what a user writes.

## How it relates to v0.8.0

**Almost entirely current.** [`#[cgp_fn]`](../cgp/reference/macros/cgp_fn.md),
[`#[implicit]`](../cgp/reference/attributes/implicit.md),
[`#[uses]`](../cgp/reference/attributes/uses.md),
[`#[extend]`](../cgp/reference/attributes/extend.md),
[`#[use_provider]`](../cgp/reference/attributes/use_provider.md), and
[`#[use_type]`](../cgp/reference/attributes/use_type.md) all exist as described, and four guides
prescribe them: [reading-context-fields](../cgp/guides/reading-context-fields.md),
[declaring-dependencies](../cgp/guides/declaring-dependencies.md),
[method-supertraits](../cgp/guides/method-supertraits.md), and
[importing-abstract-types](../cgp/guides/importing-abstract-types.md). The renamed type component is
[`HasType` / `TypeProvider`](../cgp/reference/components/has_type.md), and the checking syntax is
current in [`check_components!`](../cgp/reference/macros/check_components.md).

**One character changed.** `#[use_type(HasScalarType::Scalar)]` became
`#[use_type(HasScalarType.Scalar)]` in [v0.8.0](v0-8-0.md), a `.` where the announcement writes `::`.
This is the single most likely thing to be copied wrong from that post, because everything around it
still compiles. The equality form moved with it, to `#[use_type(HasErrorType.{Error = AppError})]`.

**Owned values need only `Clone`, as they did at this tag.** The generated code reads the field by
reference and calls `.clone()`, so the announcement's `Copy` rule is not a requirement to carry into
current code.

**Three things arrived after it.** [Namespaces](../cgp/concepts/namespaces.md) did not exist, so the
announcement's wiring examples show flat tables that a real application would now group. The `open`
statement did not exist, so nothing in it addresses
[dispatching-per-type](../cgp/guides/dispatching-per-type.md). And
[`cargo-cgp`](../cargo-cgp/README.md) did not exist, so its guidance is silent where current advice
would lead with `cargo cgp check`.

**One slip in the announcement, not in the release.** Its `HasScalarType` example declares
`type Scalar: Mul<Output = Scalar> + Copy;`, naming `Scalar` bare inside its own definition where
`Self::Scalar` is required. That syntax never worked.
