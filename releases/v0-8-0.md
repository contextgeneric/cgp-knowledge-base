# CGP v0.8.0 (unreleased)

**The release currently being prepared.** It is in development at `0.8.0-alpha`, and the website and
this knowledge base are both being brought up to date for it. Its headline feature is namespaces and
paths, which finally give component wirings a name they can be grouped under; its largest breaking
change is the removal of the entire preset system that namespaces replace.

- **Tag** — none yet. One development tag exists,
  [`v0.8.0-alpha`](https://github.com/contextgeneric/cgp/releases/tag/v0.8.0-alpha), alongside the
  `v0.8.0`, `v0.8.0-alpha`, and `v0.8.0-alpha-2` *branches*; the crates carry version `0.8.0-alpha`.
- **Announcement** — a **draft** at
  [`/blog/v0.8.0-release`](https://contextgeneric.dev/blog/v0.8.0-release), documented at
  [website/blog/v0-8-0-release.md](../website/blog/v0-8-0-release.md). It is unfinished, covers only
  namespaces, and was written under the release's old number.
- **Changelog** — none. The repository's
  [CHANGELOG.md](https://github.com/contextgeneric/cgp/blob/main/CHANGELOG.md) has no entry for this
  release; the contents below are read from the commits since
  [v0.7.0](v0-7-0.md).
- **Relation to today** — this *is* today. Everything the rest of the base documents as current
  describes v0.8.0.

## Why it is not v0.7.1

The release was begun as **v0.7.1**, a minor addition adding namespaces. It grew well past that:
namespaces required a new component-path system, the `open` statement, per-type defaults, and
ultimately the deletion of the preset mechanism they replaced, and the macro implementation was
substantially rewritten along the way. With a breaking change of that size the version was renumbered
to v0.8.0.

There is consequently **no v0.7.1 tag and there will not be one**, and the draft announcement written
under the old number now carries the v0.8.0 title. Any statement anywhere that attributes namespaces
to v0.7.1 is wrong.

## What it introduces

**Namespaces and component paths** are the headline. A component registers into a namespace under a
hierarchical path with the `#[prefix(@path in Namespace)]` attribute; `cgp_namespace!` defines a
namespace, optionally inheriting a parent; a context joins one with a `namespace` statement inside
`delegate_components!`; and an `@`-path key then bulk-delegates every component under that path to one
aggregate provider. A provider can register as a namespace's per-type default with
`#[default_impl(...)]`. Underneath, the mechanism is the `RedirectLookup` provider re-routing a lookup
along a type-level `Path!`. The effect is that a wiring table with dozens of entries collapses into a
handful of named groups, and the difference between two contexts becomes readable at a glance.

**The `open` statement** is the lightweight case of the same redirection, wired directly on one
context: `open AreaCalculatorComponent;` followed by `@AreaCalculatorComponent.Rectangle: RectangleArea`
entries dispatches a generic-parameter component per type without defining a namespace at all. It
supersedes the `UseDelegate`-plus-nested-table idiom for new code.

**`#[impl_generics]`** adds a bounded generic parameter to a `#[cgp_fn]`'s impl alone rather than to
its trait, which is how a function body can borrow a generic value it does not want to expose as a
trait parameter.

**[`cargo-cgp`](../cargo-cgp/README.md) is adopted as CGP's first-class error toolchain.** It is a
separate repository rather than part of this release, but v0.8.0 is the release that treats it as the
recommended way to build and check CGP code, which changes the answer to the most-cited obstacle to
adopting CGP.

**All documentation moves into this knowledge base.** The prose that lived in the `cgp` repository was
extracted into [`cgp-knowledge-base`](https://github.com/contextgeneric/cgp-knowledge-base), which is
why the reference, concepts, guides, errors, and implementation sections exist in their current form.
Alongside it, the [error catalog](../cgp/errors/README.md) and the
[guides section](../cgp/guides/README.md) were written from scratch.

Internally the macro implementation was reorganized: crates moved into subdirectories, most macro
logic consolidated into `cgp-macro-core`, and a snapshot-testing suite added that pins each macro's
expansion. None of that is user-facing, but it is why the
[implementation documentation](../cgp/implementation/README.md) describes the structure it does.

## What it changes or removes

**The preset system is deleted.** `cgp_preset!`, `#[cgp::re_export_imports]`, `IsPreset`,
`#[wrap_provider]`, and `#[cgp_inherit]` are all gone. Presets shipped in
[v0.4.0](v0-4-0.md) and were extended in [v0.4.1](v0-4-1.md) and [v0.6.0](v0-6-0.md); the reason for
removing them is set out in the draft announcement — a context could inherit only one preset because
of coherence, and the macro-based multiple inheritance was fragile because macros cannot see types,
so identifiers and aliases resolved unpredictably. Namespaces solve the same problem through the trait
system instead, and support the hierarchy presets could not.

**`#[use_type]` changes its separator** from `::` to `.`, so `#[use_type(HasScalarType::Scalar)]`
becomes `#[use_type(HasScalarType.Scalar)]`. The equality form
`#[use_type(HasErrorType.{Error = AppError})]` is added, which pins an abstract type to a concrete one
and replaces a hand-written associated-type-equality bound.

**Two names were used and discarded during development.** The registration attribute was first
`#[use_namespace]`, then `#[namespace]`, and finally `#[prefix]`. Neither earlier name was ever
released, but the draft announcement teaches `#[namespace(...)]`, so code copied from it will not
compile.

## How it relates to the rest of the base

This release is the baseline the whole knowledge base describes. The
[construct reference](../cgp/reference/README.md), the [concepts](../cgp/concepts/README.md), the
[guides](../cgp/guides/README.md), the [error catalog](../cgp/errors/README.md), and the
[examples](../examples/README.md) are all written against it, and the `/cgp` skill in
[`cgp-skills`](https://github.com/contextgeneric/cgp-skills) is built from them. The namespace feature
in particular is documented as the [namespaces concept](../cgp/concepts/namespaces.md), the
[`cgp_namespace!` reference](../cgp/reference/macros/cgp_namespace.md), the
[`RedirectLookup` provider](../cgp/reference/providers/redirect_lookup.md), the
[`DefaultNamespace` traits](../cgp/reference/traits/default_namespace.md), and the
[namespaces-and-prefixes guide](../cgp/guides/namespaces-and-prefixes.md), with four of its failure
modes catalogued under [cgp/errors/](../cgp/errors/README.md).

Both ecosystem projects have already migrated:
[hypershell](../projects/hypershell/README.md) assembles its contexts from a `HypershellNamespace`
rather than a preset, and [cgp-serde](../projects/cgp-serde/README.md) tracks the same alpha. Their
source is therefore a reliable reference for current CGP even where their announcement posts are not.

## What is still outstanding

Three things stand between the current state and a release, and all of them are documentation rather
than code. The **announcement post is an unfinished draft** covering one feature of several, still
teaching a superseded attribute name, with a placeholder date and an opening line claiming the release
has happened; [its document](../website/blog/v0-8-0-release.md) lists what finishing it requires. The
**changelog has no v0.8.0 entry**, and the entry above it is still mislabelled as v0.6.2 rather than
[v0.7.0](v0-7-0.md). And several **website pages predate the release** — the announcement bar still
promotes v0.7.0, the [AI skills page](../website/site-structure.md) inlines a v0.7.0-era skill, and the
Resources page does not mention `cargo-cgp` at all.
