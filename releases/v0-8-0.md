# CGP v0.8.0 (unreleased)

**The release currently being prepared.** It is in development on the `cgp` repository's `main`, and the
website and this knowledge base are both written as though it had shipped. Its headline feature is namespaces and
paths, which finally give component wirings a name they can be grouped under; its largest breaking
change is the removal of the entire preset system that namespaces replace.

- **Tag**: none yet. Pre-release tags and branches used to test the release are not tracked, per
  the base's [rule on versions](../AGENTS.md#document-official-versions-never-pre-releases).
- **Announcement**: a **draft** at
  [`/blog/v0.8.0-release`](https://contextgeneric.dev/blog/v0.8.0-release), documented at
  [website/blog/v0-8-0-release.md](../website/blog/v0-8-0-release.md). It is unfinished, covers only
  namespaces, and was written under the release's old number.
- **Changelog**: none. The repository's
  [CHANGELOG.md](https://github.com/contextgeneric/cgp/blob/main/CHANGELOG.md) has no entry for this
  release; the contents below are read from the commits since
  [v0.7.0](v0-7-0.md).
- **Relation to today**: this *is* today. Everything the rest of the base documents as current
  describes v0.8.0.

## Why it is not v0.7.1

The release was begun as **v0.7.1**, a minor addition adding namespaces. It grew well past that:
namespaces required a new component-path system, the `open` statement, per-type defaults, and
ultimately the deletion of the preset mechanism they replaced, and the macro implementation was
substantially rewritten along the way. With a breaking change of that size the version was renumbered
to v0.8.0.

There is consequently **no v0.7.1 tag and there will not be one**, and the draft announcement written
under the old number now carries the v0.8.0 title. Any statement anywhere that attributes namespaces
to v0.7.1 is wrong.

## What it introduces

**Namespaces and component paths** are the headline. A component registers into a namespace under a
hierarchical path with the `#[prefix(@path in Namespace)]` attribute; `cgp_namespace!` defines a
namespace, optionally inheriting a parent; a context joins one with a `namespace` statement inside
`delegate_components!`; and an `@`-path key then bulk-delegates every component under that path to one
aggregate provider. A provider can register as a namespace's per-type default with
`#[default_impl(...)]`. Underneath, the mechanism is the `RedirectLookup` provider re-routing a lookup
along a type-level `Path!`. The effect is that a wiring table with dozens of entries collapses into a
handful of named groups, and the difference between two contexts becomes readable at a glance.

**The `open` statement** is the lightweight case of the same redirection, wired directly on one
context: `open AreaCalculatorComponent;` followed by `@AreaCalculatorComponent.Rectangle: RectangleArea`
entries dispatches a generic-parameter component per type without defining a namespace at all. It
supersedes the `UseDelegate`-plus-nested-table idiom for new code.

**`#[impl_generics]`** adds a bounded generic parameter to a `#[cgp_fn]`'s impl alone rather than to
its trait, which is how a function body can borrow a generic value it does not want to expose as a
trait parameter.

**[`Struct!`](../cgp/reference/macros/struct.md) and [`Enum!`](../cgp/reference/macros/enum.md)**
write a record or variant shape as the body of a struct or enum declaration, expanding to exactly
the `Fields` that `#[derive(HasFields)]` gives the same body. They are also the forms cargo-cgp
prints a shape in, so a shape read in a diagnostic or an expansion can be copied back into code.
Both names join the prelude, so a crate that glob-imports the prelude alongside another crate that
exports a `Struct!` or `Enum!` macro gets an ambiguity error where it uses the name.

**[`cargo-cgp`](../cargo-cgp/README.md) is adopted as CGP's first-class error toolchain.** It is a
separate repository rather than part of this release, but v0.8.0 is the release that treats it as the
recommended way to build and check CGP code, which changes the answer to the most-cited obstacle to
adopting CGP.

**All documentation moves into this knowledge base.** The prose that lived in the `cgp` repository was
extracted into [`cgp-knowledge-base`](https://github.com/contextgeneric/cgp-knowledge-base), which is
why the reference, concepts, guides, errors, and implementation sections exist in their current form.
Alongside it, the [error catalog](../cgp/errors/README.md) and the
[guides section](../cgp/guides/README.md) were written from scratch.

Internally the macro implementation was reorganized: crates moved into subdirectories, most macro
logic consolidated into `cgp-macro-core`, the extra-feature macros given a matching
`cgp-macro-extra-core` that builds on it, and a snapshot-testing suite added that pins each macro's
expansion. Most of that is not user-facing, but it is why the
[implementation documentation](../cgp/implementation/README.md) describes the structure it does; the
parts a user can see are listed below.

## What it changes or removes

**The preset system is deleted.** `cgp_preset!`, `#[cgp::re_export_imports]`, `IsPreset`,
`#[wrap_provider]`, and `#[cgp_inherit]` are all gone. Presets shipped in
[v0.4.0](v0-4-0.md) and were extended in [v0.4.1](v0-4-1.md) and [v0.6.0](v0-6-0.md); the reason for
removing them is set out in the draft announcement: a context could inherit only one preset because
of coherence, and the macro-based multiple inheritance was fragile because macros cannot see types,
so identifiers and aliases resolved unpredictably. Namespaces solve the same problem through the trait
system instead, and support the hierarchy presets could not.

**`#[use_type]` changes its separator** from `::` to `.`, so `#[use_type(HasScalarType::Scalar)]`
becomes `#[use_type(HasScalarType.Scalar)]`. The equality form from [v0.7.0](v0-7-0.md), which pins
an abstract type to a concrete one and replaces a hand-written associated-type-equality bound, takes
the new separator too: `#[use_type(HasErrorType.{Error = AppError})]`.

**The error backends change behavior.** `cgp-error-eyre` turns on eyre's `auto-install` feature; the
0.7.0 crate builds eyre with no features, so every report it builds panics unless the application
has installed a hook with `eyre::set_hook`. It also
enables `track-caller`, and `CanRaiseError::raise_error` and `CanWrapError::wrap_error` become
`#[track_caller]`, so an eyre report's location is the line that called `raise_error`. In
`cgp-error-std`, `WrapError` prints only its detail with `{}` and the whole chain with `{:#}` and
`{:?}`, where 0.7.0 printed the source inside `Display` as well and so repeated it when a reporter
walked `source()`, and `RaiseBoxedStdError` gains an `ErrorWrapper` impl. The minimum dependencies
rise to anyhow 1.0.104 and eyre 0.6.14. The providers are rewritten with `#[cgp_impl]` and
`#[use_type]`, which changes nothing a user sees. The crates are documented in
[projects/error/](../projects/error/README.md).

**The extra-feature macro crates are renamed.** `cgp-extra-macro` and `cgp-extra-macro-lib`, the
crates that have carried `#[cgp_computer]`, `#[cgp_producer]`, and `#[cgp_auto_dispatch]` since
those macros were introduced, become `cgp-macro-extra` and `cgp-macro-extra-lib`, beside a new
`cgp-macro-extra-core`, so they read as members of the `cgp-macro*` family. Code that reaches the
macros through `cgp::prelude` is unaffected; only a crate depending on `cgp-extra-macro` directly
has to switch names.

**Those three macros now generate self-contained code, and several of their failures are fixed.**
They used to emit nested `#[cgp_new_provider]`, `delegate_components!`, and `#[cgp_computer]`
invocations naming CGP items without qualification, so they compiled only where `cgp::prelude::*`
was imported and a local item named like a CGP trait could capture a name. They now lower through
`cgp-macro-core`'s AST types and emit the final code with every name qualified, which also means an
import that existed only for the old expansion becomes unused and trips the `unused_imports` lint.
Alongside that change:

- `#[cgp_auto_dispatch]` accepts a trait with a supertrait, which it now requires of the enum, and
  names a method's elided lifetimes by the compiler's elision rules, so a named receiver lifetime, a
  trait lifetime parameter, a reference nested in another type, and an argument outlived by the
  returned borrow all compile where they used to fail. The generated per-variant computers' signatures
  change accordingly, giving each elided argument lifetime its own name.
- `#[cgp_auto_dispatch]` rejects a typed receiver such as `self: Box<Self>`, which used to
  miscompile, and an attribute argument, which it used to ignore.
- `#[cgp_computer]` and `#[cgp_producer]` accept a function named with a raw identifier, which used
  to make them panic, reject `impl Trait` in a signature with a spanned error instead of an `E0562`
  from the generated impl, and report a one-argument `Result<T>` alias with a message naming the
  `Result<T, E>` form they require rather than ``expected `,` ``.

**Two names were used and discarded during development.** The registration attribute was first
`#[use_namespace]`, then `#[namespace]`, and finally `#[prefix]`. Neither earlier name was ever
released, but the draft announcement teaches `#[namespace(...)]`, so code copied from it will not
compile.

## How it relates to the rest of the base

This release is the baseline the whole knowledge base describes. The
[construct reference](../cgp/reference/README.md), the [concepts](../cgp/concepts/README.md), the
[guides](../cgp/guides/README.md), the [error catalog](../cgp/errors/README.md), and the
[examples](../examples/README.md) are all written against it, and the `/cgp` skill in
[`cgp-skills`](https://github.com/contextgeneric/cgp-skills) is built from them. The namespace feature
in particular is documented as the [namespaces concept](../cgp/concepts/namespaces.md), the
[`cgp_namespace!` reference](../cgp/reference/macros/cgp_namespace.md), the
[`RedirectLookup` provider](../cgp/reference/providers/redirect_lookup.md), the
[`DefaultNamespace` traits](../cgp/reference/traits/default_namespace.md), and the
[namespaces-and-prefixes guide](../cgp/guides/namespaces-and-prefixes.md), with four of its failure
modes catalogued under [cgp/errors/](../cgp/errors/README.md).

Both ecosystem projects have migrated on their `v0.8.0` branches, which track this release's alpha.
On that branch [hypershell](../projects/hypershell/README.md) assembles its contexts from a
`HypershellNamespace` rather than a preset, while its `main` branch still tracks `cgp` 0.7.0 and
builds from `cgp_preset!` presets, and its published 0.1.0 crates were built against `cgp` 0.4.1.
[cgp-serde](../projects/cgp-serde/README.md) likewise tracks the alpha on `v0.8.0` and `cgp` 0.7.0 on
`main`. The `v0.8.0` branches are therefore a reliable reference for current CGP even where the
projects' announcement posts, published crates, and `main` branches are not.

## What is still outstanding

Three things stand between the current state and a release, and all of them are documentation rather
than code. The **announcement post is an unfinished draft** covering one feature of several, still
writing its prefix attributes in forms that do not compile, with a placeholder date and an opening
line claiming the release has happened; [its document](../website/blog/v0-8-0-release.md) lists what
finishing it requires. The **changelog has no v0.8.0 entry**, and the entry above it is still
mislabelled as v0.6.2 rather than [v0.7.0](v0-7-0.md). And the **website's `main` branch predates
the release**: its announcement bar still promotes v0.7.0, and its Resources page does not mention
`cargo-cgp`. The website's `v0.8.0` branch already updates both and carries the current skill under
its [AI skills section](../website/site-structure.md#ai-skills), so these land when that branch
merges.
