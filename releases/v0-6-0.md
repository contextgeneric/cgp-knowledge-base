# CGP v0.6.0

The release that made CGP look like ordinary Rust. Two weeks after [v0.5.0](v0-5-0.md), it introduces
`#[cgp_impl]`, lets a context own its wiring table directly, and removes `HasCgpProvider` — three
changes that between them retired the constructs most responsible for CGP reading as alien.

- **Tag** — [`v0.6.0`](https://github.com/contextgeneric/cgp/releases/tag/v0.6.0), 26 October 2025
- **Announcement** — [CGP v0.6.0 Release: Major ergonomic improvements for provider and context implementations](https://contextgeneric.dev/blog/v0-6-0-release),
  documented at [website/blog/v0-6-0-release.md](../website/blog/v0-6-0-release.md)
- **Changelog** — [v0.6.0](https://github.com/contextgeneric/cgp/blob/main/CHANGELOG.md)
- **Relation to today** — the two surviving changes are baseline; the compatibility scaffolding they
  shipped with is gone.

## What it introduced

**`#[cgp_impl]`** lets a provider be written as if it were a blanket impl of the consumer trait: the
context stays in the `Self` position, methods keep `&self` and their consumer-trait signatures, and
the macro rewrites the whole thing into the provider-trait shape. The announcement is careful to say
this is presentation rather than mechanism — it expands to what `#[cgp_provider]` produced — while
arguing that the presentation is the point, because the inside-out form was the single biggest
obstacle to reading CGP code.

**Direct delegation on the context** removes the separate `{Context}Components` provider struct.
`delegate_components!` can now target the context type itself, so a context is its own lookup table.
Beyond removing one level of indirection, this has a consequence the announcement draws out: because
the consumer-trait blanket impl no longer routes through a per-context provider, a context can
implement a consumer trait *directly* for components it has not delegated, freely mixing hand-written
impls with wired ones. That is what makes it safe to apply `#[cgp_component]` to an existing trait
without breaking its existing implementations — the `Hash` argument the site's
[Introduction](../website/site-structure.md) still leads with.

**`#[cgp_inherit]`** is added as a clearer way for a context to inherit a preset, replacing the
`#[cgp_context(Components: Preset)]` form.

## What it changed or removed

**`HasCgpProvider` is removed.** Consumer-trait blanket impls now route through
`DelegateComponent` exactly as provider traits do. The announcement gives the history: the original
design let several contexts share one provider table, presets made that unnecessary, and the trait
survived only for compatibility. Its removal is what unblocks direct consumer-trait impls, since the
old blanket impl covered every type implementing `HasCgpProvider` and so pre-empted any hand-written
one.

Backward compatibility was preserved rather than broken: `#[cgp_context]` was changed to emit a
blanket `impl<Name> DelegateComponent<Name> for App`, doing the same bulk-delegation job
`HasCgpProvider` had done. Both `#[cgp_context]` and `#[cgp_provider]` were **deprecated** here, with
the announcement recommending removal of the former and migration to `#[cgp_impl]` for the latter —
and noting that mixing the two provider styles confuses contributors unfamiliar with CGP.

One bug fix: use of `self` inside a default trait method body.

## How it relates to v0.8.0

**Baseline.** [`#[cgp_impl]`](../cgp/reference/macros/cgp_impl.md) is the form
[writing-providers](../cgp/guides/writing-providers.md) prescribes, with
[`#[cgp_provider]`](../cgp/reference/macros/cgp_provider.md) and
[`#[cgp_new_provider]`](../cgp/reference/macros/cgp_new_provider.md) documented as the lower layers an
agent reads rather than writes. Direct delegation on the context is how
[`delegate_components!`](../cgp/reference/macros/delegate_components.md) works throughout the base,
and the distinction this release sharpened between a context and an aggregate provider is
[aggregate providers](../cgp/concepts/aggregate-providers.md).

**Removed.** `#[cgp_context]` was deleted in [v0.7.0](v0-7-0.md), taking the compatibility shim this
release built with it — so the advice to remove it when upgrading became mandatory rather than
recommended. `#[cgp_inherit]` was removed in [v0.8.0](v0-8-0.md) along with the presets it existed to
inherit from; a context now joins a [namespace](../cgp/concepts/namespaces.md) with a `namespace`
statement inside `delegate_components!`.

**Revised once more.** The consumer-trait blanket impl this release changed was simplified again in
[v0.7.0](v0-7-0.md) to `Context: Greeter<Context>`, dropping the `DelegateComponent` lookup entirely
because the provider trait's own blanket impl already performs it. The generated code shown in the
announcement is therefore one revision stale.

**Superseded in style.** Every `#[cgp_impl]` example here still writes
`impl<Context> HttpRequestFetcher for Context`; [v0.6.1](v0-6-1.md) made the generic parameter
implicit, so current code writes `impl HttpRequestFetcher` with `Self` bounds. Dependencies are
hand-written `where Self: ...` clauses, which [v0.7.0](v0-7-0.md) replaced with
[`#[uses(...)]`](../cgp/reference/attributes/uses.md), and the hand-implemented getter in the
announcement's `HasCount` example would today be an
[`#[implicit]`](../cgp/reference/attributes/implicit.md) argument.
