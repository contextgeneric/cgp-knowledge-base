# `delegate_components!`

`delegate_components!` builds a context's type-level wiring table, implementing `DelegateComponent`
so that each component name maps to the provider that should implement it.

## Purpose

`delegate_components!` is how a concrete context chooses which provider implements each of its
components. A component created by [`#[cgp_component]`](cgp_component.md) separates the consumer
trait callers use from the provider trait implementers write, which leaves open which provider
supplies the behavior for a given context. `delegate_components!` answers that by recording one
entry per component on the context type, with the component name as the key and the chosen provider
as the value.

The table behaves like a method table that the compiler resolves. Looking a component up yields the
provider, and the blanket impls generated by `#[cgp_component]` route the consumer-trait call
through that provider. Unlike a vtable, nothing exists at runtime: the lookup is a set of trait
impls resolved during type checking, so each call compiles to a direct, statically dispatched one.

A macro is worth having because each entry expands to two impls. Besides the
[`DelegateComponent`](../traits/delegate_component.md) impl that stores the entry, the macro emits
an [`IsProviderFor`](../traits/is_provider_for.md) impl that forwards the chosen provider's
dependencies back through the table. That second impl is what lets a missing transitive requirement
surface as a readable compiler error. Writing both by hand for every component on every context
would be tedious and easy to get wrong.

## Syntax

The macro takes an optional generic list and `new` keyword, a target type, and a braced body. The
body holds any number of **statements** followed by any number of **mappings**. A mapping is a key,
an operator, and a value, and each is chosen independently from a small set: three operators, three
key forms, and two value forms. The three statements generate entries of their own.

All of these forms combine inside one block, and combining them is normal. A single table routinely
opens a component for per-type dispatch, joins a namespace, loops over another table's entries, and
maps plain component names to providers. The only ordering rule is that statements come before
mappings.

The parser couples none of the three choices, so every operator accepts every key form. Only some
combinations are useful, and each subsection below says which. Treating the grammar as a menu is how
a table ends up with an entry that expands correctly and resolves to nothing.

### The table header: target, `new`, and generics

The simplest table names a target type and lists `Key: Value` entries in braces. The target is the
context, or an [aggregate provider](../../concepts/aggregate-providers.md), whose table is being
defined. Each key is a component-name type and each value is the provider to delegate that component
to:

```rust
delegate_components! {
    Rectangle {
        AreaCalculatorComponent: RectangleAreaCalculator,
    }
}
```

A `new` keyword before the target makes the macro declare the target struct as well.
`new MyComponents { ... }` emits `pub struct MyComponents;`, or a generic struct with a
`PhantomData` field when the target carries lifetime or type parameters, alongside the table impls.
A `const` parameter is not supported there, as Known issues records. This is how
an aggregate provider is declared: a zero-sized provider whose table dispatches each component to a
sub-provider, so other contexts can delegate a whole group of components to it at once.

An aggregate provider is a provider rather than a context, so it is wired with plain
`delegate_components!` and never with
[`delegate_and_check_components!`](delegate_and_check_components.md). The fused macro's check asks
whether the target can use each component as a context, which is the wrong question for a bundle: it
passes vacuously when the bundled providers need nothing from their context and blames the bundle
when they do. That macro's reference works both outcomes through.

A leading `<...>` generic list makes the whole table generic, so one table wires a family of context
types. `delegate_components! { <T> MyContext<T> { ... } }` wires every `MyContext<T>`, and the list
is threaded onto every impl the block generates.

### Operators: `:`, `->`, and `=>`

The operator decides what an entry's `Delegate` resolves to.

**`Key: Provider` names the provider directly**, and nearly all wiring uses it. The entry's
`Delegate` is the value as written, so `AreaCalculatorComponent: RectangleAreaCalculator` means "for
this component, this context uses `RectangleAreaCalculator`".

**`Key -> Table` forwards to the value's own entry for the same key**, which is called direct
delegation. The entry's `Delegate` becomes `<Table as DelegateComponent<Key>>::Delegate`, and the
macro adds a `Table: DelegateComponent<Key>` bound, so the entry compiles only when that table has
an entry for the key. One table can adopt a single entry from another this way without naming the
provider, so a bundle's choice for a component tracks another bundle's choice:

```rust
delegate_components! {
    new BarComponents {
        Index<0>:
            FooComponents,      // the provider *is* FooComponents
        Index<1> ->
            FooComponents,      // the provider is whatever FooComponents wires for Index<1>
    }
}
```

The two lines differ in a way that is easy to miss. The `:` entry hands the whole lookup to
`FooComponents` as a provider, while the `->` entry reaches into `FooComponents`'s table and copies
out the value it holds for that key.

**`Key => @path` redirects the lookup along a type-level path.** The entry's `Delegate` becomes a
[`RedirectLookup`](../providers/redirect_lookup.md) over the table type and the path, so the real
provider is whatever the path finally reaches. The value is a plain [`@`-path](path.md) of dotted
segments, without groups or per-segment generics. On a context, the path names a slot in the
context's own table, so several components can point at one shared slot and be answered by a single
entry:

```rust
delegate_components! {
    App {
        [BarProviderComponent, BazProviderComponent] =>
            @shared,

        @shared: DummyImpl,
    }
}
```

What the path lowers to depends on the key. Against a plain key it is a complete `PathCons` list
ending in `Nil`. Against an `@`-path key, both sides are lowered as prefixes ending in the same
`__Wildcard__` parameter, so the entry rewrites one path prefix into another and passes the rest
through unchanged. That second form reroutes a whole subtree of routes at once, and it is the
mechanism behind the path-rewriting entries described under [`cgp_namespace!`](cgp_namespace.md).

The redirect operator also explains the `open` statement: `open AreaCalculatorComponent;` generates
the same impl as `AreaCalculatorComponent => @AreaCalculatorComponent,`.

### Keys: a single name, a list, or a path

A key takes one of three forms. A single key and a path key may each carry their own leading generic
list, which merges with the table's. A list key carries none of its own, but each of its elements is
a single key and may carry one.

**A single key is one component-name type**, optionally preceded by the generics it introduces.
`AreaCalculatorComponent: RectangleAreaCalculator` is the common case, and
`<T2> BazKey<T1, T2>: BazProvider` adds a parameter to that entry's impls alone. A generic key is
either a plain lookup type or a component marker that carries the trait's parameters through the
`name:` key of [`#[cgp_component]`](cgp_component.md), as in
`<Shape> ShapeAreaCalculatorComponent<Shape>: SumAreas`; such a component's provider names the
parameterized marker explicitly, as
`#[cgp_impl(new SumAreas: ShapeAreaCalculatorComponent<Shape>)]`.

**A list key is a bracketed list of single keys**, and it expands to one entry per element so that
several components share one value:

```rust
delegate_components! {
    MyComponents {
        [
            FooComponent,
            BarComponent,
        ]: FooBarProvider,
        BazComponent: BazProvider,
    }
}
```

Each element is a full single key and may carry its own generics: in the table
`<T1: Clone> GenericKeyComponents { [BarKey<T1>, <T2> BazKey<T1, T2>]: BarValue<T1>, … }`, only the
second element introduces `T2`. The list itself takes no generic list: `<T> [BarKey<T>, BazKey]`
fails with `expected square brackets` at the `<`, because the key parser peeks past the generics,
sees the bracket, and hands the whole key to the list parser. The list is a key form, not an
operator, so `[A, B] -> SomeTable` and `[A, B] => @somewhere` are as legal as `[A, B]: Provider`.
The first adopts several of another table's entries at once, and the second points several
components at one shared slot.

**A path key is an `@`-prefixed route** rather than a component name, and it addresses an entry
behind a redirect: the per-value slots an `open` statement opens, or the prefixed routes a namespace
registers. `@AreaCalculatorComponent.Rectangle: RectangleAreaCalculator` stores the provider at the
position the `AreaCalculatorComponent` redirect reaches when the dispatch parameter is `Rectangle`.
Segments follow the [`Path!`](path.md) convention: a lowercase identifier that is not a primitive
type becomes a `Symbol!` string, and any other segment is a type. Any segment may carry its own
generics, as in `@SomeComponent.<'a, T> &'a T: SomeProvider`.

Two grouping forms fan a path key out into several keys, and they are not interchangeable:

- **A bracketed group, `[…]`, holds alternatives for one segment** and may be followed by more path.
  `@app.[FooComponent, BarComponent].[u64, String]: DummyImpl` expands to the four keys of the
  cartesian product.
- **A braced group, `{…}`, holds alternative tails and ends the path.** Each element is a complete
  remainder, so elements may differ in length and nest further groups, and nothing may follow the
  closing brace.

The braced form is what lets one entry cover routes of different shapes:

```rust
delegate_components! {
    App {
        namespace ExtendedNamespace;

        @app.{
            ErrorRaiserComponent.{&'static str, String},
            ErrorWrapperComponent,
        }: RaiseFrom,
    }
}
```

In short, `[…]` is a choice within a segment and `{…}` is a choice of tails. Both produce one key
per combination.

Every bracketed and braced list, including the list key and `open { … }`, also parses when empty. An
empty list produces no entries and no error.

### Values: a provider type, or a nested table

The value of a `:` or `->` mapping is normally a type: the provider, or the table being forwarded
to. One further form exists, and it is legacy.

> **Legacy:** A value may open a nested table, the older way to dispatch a component on a generic parameter. Writing `UseDelegate<new InnerComponents { ... }>` as the value wires the outer key to [`UseDelegate`](../providers/use_delegate.md) over an inner table and defines that table in place:
>
> ```rust
> delegate_components! {
>     MyApp {
>         AreaCalculatorComponent:
>             UseDelegate<new AreaCalculatorComponents {
>                 Rectangle: RectangleAreaCalculator,
>                 Circle: CircleAreaCalculator,
>             }>,
>     }
> }
> ```
>
> Three details of the form are not visible in that example:
>
> - **The inner braces hold a full table body**, so an inner table accepts every form this section describes, including further nesting.
> - **The wrapper is not fixed to `UseDelegate`.** Any wrapper named by a single identifier is accepted, and the macro substitutes the generated table type for the `new …` block. So a component whose `#[derive_delegate]` names a wrapper of the user's own, such as a `UseDelegate2` keyed on a tuple of its parameters, is wired the same way. The wrapper must be a bare identifier: a qualified `cgp::prelude::UseDelegate<new Inner { … }>` fails the nested-table parse, falls back to a plain type, and reports ``expected `,` `` at the inner table's name.
> - **The inner table's name may carry type generics**, which a per-entry generic on the outer key threads into:
>
> ```rust
> delegate_components! {
>     new MyComponents {
>         <T> BarKey<T>: UseDelegate<new BarValue<T> {
>             BazKey: BazValue<T>,
>         }>,
>     }
> }
> ```
>
> Here the entry's `<T>` reaches the outer key, the wrapper, and the generated `struct BarValue<T>` alike, so one entry defines a family of inner tables.
>
> The form also depends on the component carrying [`#[derive_delegate(UseDelegate<Shape>)]`](../attributes/derive_delegate.md), which generates the dispatch impl the wrapper resolves through. Without it the table still expands, and the failure appears at the check as an unsatisfied `IsProviderFor` on `UseDelegate<…>` that says nothing about the missing attribute. This is the practical difference from `open`, which resolves through the `RedirectLookup` impl every component already has and so needs nothing added to the component.
>
> The nested-table value, the `UseDelegate` provider, and `#[derive_delegate]` together make up the legacy dispatch mechanism. The `open` statement gives the same per-type dispatch without a separate inner table or a wrapper, and is preferred for new code. The nested form remains for compatibility and is expected to be deprecated once `open` is shown to cover every dispatch case.

### Statements: `open`, `namespace`, and `for`

A statement generates entries without being written as a `Key OP Value` mapping, and every statement
must come before the first mapping. The ordering is a parse rule, so a statement written after a
mapping fails with a message about an unexpected token rather than about its position, as Known
issues shows. Several statements may appear, in any order among themselves.

**`open` opens components for per-value wiring in the context's own table**, and it is the
recommended way to dispatch a component on a type parameter. The statement wires each listed
component to a redirect rooted at the component's name, after which `@Component.Key` path keys fill
the per-value slots:

```rust
delegate_components! {
    MyApp {
        open AreaCalculatorComponent;

        @AreaCalculatorComponent.Rectangle: RectangleAreaCalculator,
        @AreaCalculatorComponent.Circle: CircleAreaCalculator,
    }
}
```

`MyApp` then computes a `Rectangle`'s area with `RectangleAreaCalculator` and a `Circle`'s with
`CircleAreaCalculator`, without naming a separate table. The braces are optional for one component,
so `open AreaCalculatorComponent;` and `open { AreaCalculatorComponent };` are the same, while
several components need the braced list.

`open` resolves through the [`RedirectLookup`](../providers/redirect_lookup.md) impl every
[`#[cgp_component]`](cgp_component.md) generates, so it needs no
[`#[derive_delegate]`](../attributes/derive_delegate.md) on the component. It is a lightweight form
of the full [namespace](cgp_namespace.md) feature, suited to a context that wires its own components
directly. It does not combine with a component registered in a joined namespace through
`#[prefix(...)]`; there, the per-value entries are written with the full prefixed path.

An `open` key can dispatch on any of the component's type parameters, not only the first. The
redirect appends every type parameter of the consumer trait to the path, in declaration order, so a
lookup of `CanCompute<Code, Input>` follows `@ComputerComponent.Code.Input`. A key that stops after
one segment matches that value of the first parameter with any value of the rest, and a longer key
dispatches on the later parameters too. A per-entry generic in the first segment dispatches on a
later parameter alone, which replaces a legacy `UseInputDelegate` table:

```rust
delegate_components! {
    Interpreter {
        open ComputerComponent;

        @ComputerComponent.<Code> Code.MathExpr: DispatchEval,
        @ComputerComponent.<Code> Code.Plus<MathExpr>: EvalAdd,
        @ComputerComponent.<Code> Code.Times<MathExpr>: EvalMultiply,
        @ComputerComponent.<Code> Code.Literal<Value>: EvalLiteral,
    }
}
```

Here `Interpreter` evaluates each variant of the
[expression interpreter](../../../examples/expression-interpreter.md)'s `MathExpr` with its own
provider, whatever `Code` the caller passes. Concrete segments dispatch on both parameters at once,
so `@ComputerComponent.Eval.Literal<u64>: EvalLiteral` and
`@ComputerComponent.Show.Literal<u64>: ShowLiteral` give one input two operations. A per-entry
generic may carry a bound, as in
`@HandlerComponent.<Handlers: WrapCall> Pipe<Handlers>: PipeHandlers<Handlers::Wrapped>`.

A shorter key covers every longer key beneath it, because each key ends in a wildcard. So
`@ComputerComponent.Eval` and `@ComputerComponent.Eval.Literal<u64>` in one table overlap and fail
with `E0119`, and a value of the first parameter is keyed either on its own or per later parameter,
never both. A per-entry generic segment matches every value in its position, so
`@ComputerComponent.<Code> Code.Literal<u64>` overlaps `@ComputerComponent.Eval` as well; a table
that dispatches on the input alone keys no code on its own.

**`namespace` joins the context to a [namespace](cgp_namespace.md)**, so every lookup the table does
not wire directly is answered through the namespace's trait. `namespace DefaultNamespace;` emits a
single blanket `DelegateComponent` impl covering every key the namespace resolves. A direct entry
for a key the namespace itself binds therefore conflicts with it, as Known issues describes.

**`for` copies entries out of another lookup table.** It binds a key variable and a value variable
and emits one entry per mapping in its body, answered through the table named after `in`. Its body
holds only `:` mappings, and its optional `where` clause is added to every impl the loop generates:

```rust
delegate_components! {
    AppB {
        namespace DefaultNamespace;

        for <T, Provider> in DefaultShowComponents {
            @test.ShowImplComponent.T: Provider,
        }
    }
}
```

`namespace` and `for` belong to the namespace machinery, and [`cgp_namespace!`](cgp_namespace.md)
owns their grammar and the per-type-default pattern `for` exists for.

### Combining the forms

A real context's table often uses several forms at once. The block below opens a component for
per-type dispatch, forwards one component into an aggregate provider's table with `->`, shares a
provider across a list key, and fans path keys out with both group syntaxes:

```rust
delegate_components! {
    App {
        open AreaCalculatorComponent;

        BarProviderComponent -> BarBundle,

        [BazProviderComponent, QuuxProviderComponent]: DummyBaz,

        @AreaCalculatorComponent.{Rectangle, Circle}:
            ShapeArea,

        @AreaCalculatorComponent.[Square, Triangle]:
            PolygonArea,
    }
}
```

The block is still one table. Every line lowers to the same `DelegateComponent` and `IsProviderFor`
impl pair; the syntaxes differ only in how many entries a line produces and what each entry's
`Delegate` is.

### Attributes are rejected

The macro accepts no attributes anywhere: not on the table, on a key, on a key inside a `for` loop,
or on a key inside a nested `UseDelegate<new Inner { … }>` value. It rejects each with a spanned
`unsupported attribute: …` error rather than discarding it. The attribute-driven variants,
`#[check_params(...)]` and `#[skip_check]`, belong to
[`delegate_and_check_components!`](delegate_and_check_components.md).

## Syntax Grammar

The body of `delegate_components!` is an optional generic list and `new` keyword, a target type, and
a braced table of statements and mappings:

```ebnf
DelegateComponents -> Generics? `new`? TargetType `{` TableBody `}`

TargetType    -> Type

TableBody     -> Statement* ( Mapping ( `,` Mapping )* `,`? )?

Statement     -> OpenStmt | NamespaceStmt | ForStmt

OpenStmt      -> `open` ( `{` ( Type ( `,` Type )* `,`? )? `}` | Type ) `;`
// NamespaceStmt and ForStmt are defined under cgp_namespace!

Mapping       -> NormalMapping
               | Key `->` ProviderValue
               | Key `=>` PathValue

NormalMapping -> Key `:` ProviderValue

Key           -> SingleKey | MultiKey | PathKey
SingleKey     -> Generics? Type
MultiKey      -> `[` ( SingleKey ( `,` SingleKey )* `,`? )? `]`
PathKey       -> Generics? `@` PathHead

PathHead      -> KeySegment ( `.` PathHead )?
               | `[` ( KeySegment ( `,` KeySegment )* `,`? )? `]` ( `.` PathHead )?
               | `{` ( PathHead ( `,` PathHead )* `,`? )? `}`

KeySegment    -> Generics? PathSegment

PathValue     -> `@` PathSegment ( `.` PathSegment )*      // see Path!

PathSegment   -> Type

ProviderValue -> Type
               | IDENTIFIER `<` `new` InnerTable `>`

InnerTable    -> IDENTIFIER BoundFreeGenerics? `{` TableBody `}`
```

The grammar needs a few notes beyond what the rules show:

- **Operators and keys are independent.** Each `Mapping` chooses an operator regardless of its key
  form. `NormalMapping` is named separately only because a `ForStmt` body admits nothing else.
- **The three segment productions differ in what they permit.** A `KeySegment`, a segment of a
  `PathKey`, takes an optional leading `Generics` list whose parameter lands on that entry's impls,
  and the generics of every segment along a path are merged. A `PathSegment`, a segment of a
  `PathValue`, takes no generics and admits no groups; it is exactly the production
  [`Path!`](path.md) defines. A bracketed group holds alternative `KeySegment`s and may continue,
  while a braced group holds whole `PathHead` tails and ends the path.
- **Key generics are impl-position lists.** Every `Generics` on a key accepts bounds, as in
  `<T: Clone> BazKey<T>: BazProvider`, but rejects a parameter default, which fails with
  `invalid impl generics syntax`.
- **An `InnerTable` names a fresh struct.** It is an identifier with an optional `BoundFreeGenerics`
  list rather than a full type, because the macro declares it. That list is a definition-position
  list of lifetimes and type parameters: no bounds and no defaults. Write any bound on the entry's
  generics instead. A bound on the inner table is rejected, but with a misleading message: the value
  parser tries the nested form speculatively and falls back to a plain type, so
  `UseDelegate<new BarValue<T: Clone> { … }>` reports ``expected `,` `` at the inner table's name.
  A `const N: usize` parameter fails the same way, and a bare `N` declares a type parameter, so an
  entry passing a const through it fails with `E0747`: an inner table cannot carry a const
  parameter, as Known issues records.
- **The nested-table wrapper is a bare `IDENTIFIER`.** A qualified path is not the nested form and
  reports ``expected `,` `` like a bound does.
- **A `MultiKey` takes no generics of its own**, only its elements do.
- **Empty lists parse.** An empty `open { }`, list key, or path group is accepted and produces no
  entries.
- **Statements lead.** Every `Statement` precedes every `Mapping`, as `TableBody` requires.

`Mapping`, `NormalMapping`, `Key`, `PathKey`, and `ProviderValue` are shared with
[`delegate_and_check_components!`](delegate_and_check_components.md) and
[`cgp_namespace!`](cgp_namespace.md).

## Expansion

Each table entry expands to a pair of impls: a `DelegateComponent` impl that stores the value, and
an `IsProviderFor` impl that forwards the value's dependencies. Given the single-entry table:

```rust
delegate_components! {
    Rectangle {
        AreaCalculatorComponent: RectangleAreaCalculator,
    }
}
```

the macro first emits the `DelegateComponent` impl recording `AreaCalculatorComponent` as the key
and `RectangleAreaCalculator` as the `Delegate`:

```rust
impl DelegateComponent<AreaCalculatorComponent> for Rectangle {
    type Delegate = RectangleAreaCalculator;
}
```

This impl is what the provider blanket impl from [`#[cgp_component]`](cgp_component.md) reads.
Because `Rectangle` delegates `AreaCalculatorComponent` to `RectangleAreaCalculator`, `Rectangle`
inherits `AreaCalculator<Rectangle>` from it, and the consumer blanket impl then gives `Rectangle`
the `CanCalculateArea` consumer trait. The hand-written equivalent of one entry is exactly this
`impl DelegateComponent<…>` block.

The macro then emits the matching `IsProviderFor` impl, generic over a context and a params tuple,
which holds whenever the delegated provider is itself a provider for the component:

```rust
impl<__Context__, __Params__>
    IsProviderFor<AreaCalculatorComponent, __Context__, __Params__> for Rectangle
where
    RectangleAreaCalculator: IsProviderFor<AreaCalculatorComponent, __Context__, __Params__>,
{}
```

This second impl keeps missing dependencies diagnosable. `RectangleAreaCalculator`'s own
`IsProviderFor` impl, generated by [`#[cgp_impl]`](cgp_impl.md) or
[`#[cgp_provider]`](cgp_provider.md), carries the bounds it needs, so an unmet transitive
requirement flows back through this forwarding impl to the point of use. The parameters are
literally named `__Context__` and `__Params__`.

Every other form lowers to the same pair, including the three statements. What a form changes is how
many pairs one line produces and what the `Delegate` type is, as the rest of this section shows.

### List keys repeat the pair per name

A list key repeats the pair once per element. The table:

```rust
delegate_components! {
    MyComponents {
        [FooComponent, BarComponent]: FooBarProvider,
        BazComponent: BazProvider,
    }
}
```

expands as if each element were written on its own line, giving three `DelegateComponent` impls
(`FooComponent` and `BarComponent` to `FooBarProvider`, `BazComponent` to `BazProvider`) and their
three `IsProviderFor` impls.

### Direct delegation projects the value's own entry

A `->` mapping keeps the pair but makes the `Delegate` a projection through the value's table, and
adds the bound that makes the projection well-formed. From `Index<1> -> FooComponents`:

```rust
impl DelegateComponent<Index<1>> for BarComponents
where
    FooComponents: DelegateComponent<Index<1>>,
{
    type Delegate = <FooComponents as DelegateComponent<Index<1>>>::Delegate;
}
```

The forwarding `IsProviderFor` impl carries that bound as well as the usual one, stated about the
projected type:

```rust
impl<__Context__, __Params__> IsProviderFor<Index<1>, __Context__, __Params__>
for BarComponents
where
    FooComponents: DelegateComponent<Index<1>>,
    <FooComponents as DelegateComponent<Index<1>>>::Delegate:
        IsProviderFor<Index<1>, __Context__, __Params__>,
{}
```

### Redirection wires a `RedirectLookup`

A `=>` mapping sets the `Delegate` to a [`RedirectLookup`](../providers/redirect_lookup.md) over the
table type and the path. Against a plain key the path is complete, so
`FooProviderComponent => @MyFooComponent` yields
`RedirectLookup<Table, PathCons<MyFooComponent, Nil>>`. Against an `@`-path key both sides end in
the shared `__Wildcard__` parameter. So `@cgp.core.error => @app` maps the key prefix
`PathCons<"cgp", PathCons<"core", PathCons<"error", __Wildcard__>>>` onto the value prefix
`PathCons<"app", __Wildcard__>`, rewriting one prefix into the other and passing the rest through.

### The nested-table value lifts an inner table out

A nested-table value expands in two parts: the inner table is lifted into its own table definition,
and the outer entry is wired to the wrapper over the inner table's type. The earlier `MyApp` example
is equivalent to:

```rust
delegate_components! {
    MyApp {
        AreaCalculatorComponent: UseDelegate<AreaCalculatorComponents>,
    }
}

delegate_components! {
    new AreaCalculatorComponents {
        Rectangle: RectangleAreaCalculator,
        Circle: CircleAreaCalculator,
    }
}
```

Because the inner value was written with `new`, the macro also declares
`struct AreaCalculatorComponents;`. `MyApp`'s table maps `AreaCalculatorComponent` to
`UseDelegate<AreaCalculatorComponents>`, and `AreaCalculatorComponents` is a second table whose
`Rectangle` and `Circle` entries tell `UseDelegate` which provider to use for each shape;
[`UseDelegate`](../providers/use_delegate.md) describes that inner lookup. This is the legacy form,
and the `open` expansion below is its modern equivalent.

### `open` expands to a redirect plus wildcard-tailed entries

The `open` statement expands each listed component to a redirect entry, and the per-value mappings
are stored on the context itself. From:

```rust
delegate_components! {
    MyApp {
        open AreaCalculatorComponent;

        @AreaCalculatorComponent.Rectangle: RectangleAreaCalculator,
        @AreaCalculatorComponent.Circle: CircleAreaCalculator,
    }
}
```

the `open AreaCalculatorComponent;` statement wires `AreaCalculatorComponent` to a `RedirectLookup`
rooted at the component name inside `MyApp`'s own table:

```rust
impl DelegateComponent<AreaCalculatorComponent> for MyApp {
    type Delegate = RedirectLookup<MyApp, PathCons<AreaCalculatorComponent, Nil>>;
}
```

This is the same impl the mapping `AreaCalculatorComponent => @AreaCalculatorComponent,` produces,
which is the precise sense in which `open` is sugar for a `=>` entry.

Each `@AreaCalculatorComponent.Rectangle: RectangleAreaCalculator` entry then stores its provider in
the same table under the path key, generic over the path's tail:

```rust
impl<__Wildcard__>
    DelegateComponent<PathCons<AreaCalculatorComponent, PathCons<Rectangle, __Wildcard__>>>
    for MyApp
{
    type Delegate = RectangleAreaCalculator;
}
```

The [`RedirectLookup`](../providers/redirect_lookup.md) impl that
[`#[cgp_component]`](cgp_component.md) generates for `AreaCalculator` appends the dispatch
parameter, here `Rectangle`, to the redirect path and looks the result up, so
`MyApp: CanCalculateArea<Rectangle>` resolves to `RectangleAreaCalculator`. The key's tail is a
generic `__Wildcard__` rather than `Nil`, so the entry matches any path that begins with that
component and parameter, whatever the lookup appends after it. An entry ending in `Nil` would answer
only a path of exactly that length. [`cargo cgp expand`](../cargo-cgp.md) resugars the redirect
target in the `open` impl to `Path!(@AreaCalculatorComponent)` but prints each entry's key as the
raw `PathCons` list, so one expansion shows the same kind of type in both spellings.

A component with several type parameters appends them all, in declaration order, through the
`ConcatPath` bound on its `RedirectLookup` impl; lifetime and const parameters are not appended. So
`@ComputerComponent.<Code> Code.Plus<MathExpr>: EvalAdd` expands to an impl generic over both the
entry's `Code` and the wildcard, answering `CanCompute<Code, Plus<MathExpr>>` for every `Code`:

```rust
impl<Code, __Wildcard__>
    DelegateComponent<PathCons<ComputerComponent, PathCons<Code, PathCons<Plus<MathExpr>, __Wildcard__>>>>
    for Interpreter
{
    type Delegate = EvalAdd;
}
```

Because the tail after the last written segment is always a wildcard, a key's impl covers every
longer key sharing its segments. That is why a one-segment key and a two-segment key beneath it
cannot share a table.

### Path groups expand to the cartesian product

A grouped path key expands to one impl pair per combination.
`@app.[FooProviderComponent, BarProviderComponent].[u64, String]: DummyImpl` emits four
`DelegateComponent` impls, each keyed on a full path prefix ending in `__Wildcard__`:

```rust
impl<__Wildcard__>
    DelegateComponent<
        PathCons<Symbol!("app"), PathCons<FooProviderComponent, PathCons<u64, __Wildcard__>>>,
    > for App
{
    type Delegate = DummyImpl;
}
// … and likewise for (Foo, String), (Bar, u64), and (Bar, String)
```

A braced group behaves the same way, except that its alternatives are whole tails, so
`@app.{ErrorRaiserComponent.{&'static str, String}, ErrorWrapperComponent}` yields three keys of two
different lengths. The lowercase `app` segment is a `Symbol!` string in every case, per
[`Path!`](path.md).

### `namespace` and `for` expand to namespace-bounded impls

The two namespace statements share one lowering. Both build an impl generic over a `__Key__` and a
`__Value__`, bounded on the namespace trait with the table type and a `Delegate = __Value__`
binding, which makes the namespace's answer the context's answer. A bare
`namespace DefaultNamespace;` produces this blanket `DelegateComponent` impl, with its forwarding
`IsProviderFor` impl beside it:

```rust
impl<__Key__, __Value__> DelegateComponent<__Key__> for App
where
    __Key__: DefaultNamespace<App, Delegate = __Value__>,
{
    type Delegate = __Value__;
}
```

A `for <T, Provider> in SomeTable { … }` loop produces the same shape once per mapping in its body,
with the loop's variables in the bound, the mapping's key and value in the impl, and any predicates
its `where` clause adds. [`cgp_namespace!`](cgp_namespace.md) carries the worked examples.

## Examples

A complete wiring shows the table feeding the consumer trait. This first example wires a value
context: `Rectangle` is the shape whose area the self-targeted component computes. Given a component
and a provider:

```rust
use cgp::prelude::*;

#[cgp_component(AreaCalculator)]
pub trait CanCalculateArea {
    fn area(&self) -> f64;
}

#[cgp_impl(new RectangleAreaCalculator)]
impl AreaCalculator {
    fn area(&self, #[implicit] width: f64, #[implicit] height: f64) -> f64 {
        width * height
    }
}
```

a concrete context wires the component, checks the wiring, and calls through it:

```rust
#[derive(HasField)]
pub struct Rectangle {
    pub width: f64,
    pub height: f64,
}

delegate_components! {
    Rectangle {
        AreaCalculatorComponent: RectangleAreaCalculator,
    }
}

check_components! {
    Rectangle {
        AreaCalculatorComponent,
    }
}

fn print_area(rect: &Rectangle) {
    println!("area = {}", rect.area()); // resolves via Rectangle's table to RectangleAreaCalculator
}
```

The payoff appears when a second context answers the same trait differently. It writes its own
provider and its own entry, and code calling `area()`, including any function generic over
`CanCalculateArea`, does not change:

```rust
#[cgp_impl(new SquareAreaCalculator)]
impl AreaCalculator {
    fn area(&self, #[implicit] side: f64) -> f64 {
        side * side
    }
}

#[derive(HasField)]
pub struct Square {
    pub side: f64,
}

delegate_components! {
    Square {
        AreaCalculatorComponent: SquareAreaCalculator,
    }
}

check_components! {
    Square {
        AreaCalculatorComponent,
    }
}
```

Each context's choice stays one searchable line, and finding it tells a reader which implementation
runs.

An [aggregate provider](../../concepts/aggregate-providers.md) uses `new` to declare its own table
type, which contexts can then delegate to as one unit:

```rust
delegate_components! {
    new GeometryComponents {
        AreaCalculatorComponent: RectangleAreaCalculator,
        PerimeterCalculatorComponent: RectanglePerimeterCalculator,
    }
}
```

Per-shape dispatch needs a different arrangement. The component becomes parameter-targeted,
`CanCalculateArea<Shape>`, and the wired type becomes an environmental context, `MyApp`, which
carries only the wiring. The context opens the component and fills the per-value slots with path
keys:

```rust
#[cgp_component(AreaCalculator)]
pub trait CanCalculateArea<Shape> {
    fn area(&self, shape: &Shape) -> f64;
}

pub struct MyApp;

delegate_components! {
    MyApp {
        open AreaCalculatorComponent;

        @AreaCalculatorComponent.Rectangle: RectangleAreaCalculator,
        @AreaCalculatorComponent.{Circle, Ellipse}: CurveAreaCalculator,
    }
}

check_components! {
    MyApp {
        AreaCalculatorComponent: [Rectangle, Circle, Ellipse],
    }
}
```

Here the providers read the shape's fields from the `shape` argument rather than from the context.
[Choosing a component's shape](../../guides/choosing-a-component-shape.md) explains when to move
from the first arrangement to the second.

## Known issues

Several failure modes recur, and none reports itself as a wiring problem.

**Wiring is lazy, so a wrong table still compiles.** A missing entry, or an entry naming a provider
whose dependencies are unmet, produces no error at the `delegate_components!` site. The failure
appears wherever the trait is finally used, as an `E0277` or `E0599` cascade over generated types.
This is the [hidden unsatisfied-dependency class](../../errors/hidden/unsatisfied-dependency.md).
Pair the table with [`check_components!`](check_components.md) so the failure is reported at the
wiring, and read it through [`cargo cgp check`](../cargo-cgp.md), which recovers the cause the
compiler hides.

**A value naming a provider struct that was never declared** reports as an unresolved type, `E0425`
``cannot find type `SquareArea` in this scope``, rather than anything about wiring. The usual cause
is a provider written with [`#[cgp_impl]`](cgp_impl.md) without the `new` keyword and never declared
separately, since the bare form implements the provider trait for a struct the author is expected to
write.

**A statement placed after a mapping fails to parse**, and the message points somewhere misleading.
Once the statements are consumed the parser expects only mappings, so it reads `open` as a key type,
looks for an operator after it, and finds the component name:

```rust
delegate_components! {
    App {
        BarProviderComponent: DummyBar,

        open FooProviderComponent;
    }
}
```

```text
error: expected `:`
```

The caret lands on `FooProviderComponent`, blaming the component rather than the misplaced `open`,
and nothing mentions that statements must lead. A braceless `open` listing more than one component
fails similarly, with ``expected `;` `` at the first comma, because the braceless form reads exactly
one component.

**A braced path group followed by more path fails to parse**, and the message says nothing about
groups. A braced group holds whole tails and ends the path, so writing:

```rust
@FooProviderComponent.{String, u32}.bool: DummyFoo,
```

leaves `.bool` where the parser expects the mapping's operator:

```text
error: expected `:`
```

The caret lands on the dot after the closing brace. Use a bracketed group when the path continues
past the alternatives, as in `@FooProviderComponent.[String, u32].bool`, and a braced group only at
the end.

**Overlapping entries are reported by the compiler as `E0119`**, not by the macro. Two entries
claiming the same key are the [conflicting wiring](../../errors/wiring/conflicting-wiring.md) class.
The error arrives twice, once for the entry's `DelegateComponent` impl and once for its
`IsProviderFor` impl, both on the later entry's key.
The overlap can be indirect: an `open` statement colliding with an explicit mapping for the same
component, a generic `<T> Wrapper<T>` entry overlapping a specific `Wrapper<u64>` one, or a path key
overlapping a longer one beneath it, such as `@ComputerComponent.Eval` beside
`@ComputerComponent.Eval.Literal<u64>` or `@ComputerComponent.<Code> Code.Literal<u64>`. A direct
entry for a path that a joined namespace itself binds overlaps the blanket impl of the `namespace`
statement, which is the
[namespace override conflict](../../errors/wiring/namespace-override-conflict.md) class. Overriding
works only on a path the namespace routes onward without binding.

**A table struct the macro declares cannot carry a `const` parameter.** A nested inner table's
generic list admits only lifetimes and type parameters, so
`UseDelegate<new ArrayTable<const N: usize> { … }>` fails to parse, reporting ``expected `,` `` at
`ArrayTable` once the value parser falls back to a plain type. Writing the bare `N` parses, but
declares `N` as a type parameter of the generated struct, so an entry keyed on
`<const N: usize> ArrayKey<N>` that passes `N` through fails with `E0747`, a constant provided where
a type was expected. A `new` target fails the same way: `<const N: usize> new ArrayTable<N> { … }`
declares `ArrayTable<N>` with a type parameter and reports `E0747`, because the target's struct is
read from its type arguments, which name `N` without its kind. The workaround is to declare the
struct by hand, `pub struct ArrayTable<const N: usize>;`, wire it with its own block,
`<const N: usize> ArrayTable<N> { … }`, and name it in the outer entry as
`UseDelegate<ArrayTable<N>>`.

## Related constructs

These constructs are the ones `delegate_components!` works with:

- [`#[cgp_component]`](cgp_component.md): defines the components this macro wires, and the
  `RedirectLookup` impl that `open` resolves through.
- [`#[cgp_impl]`](cgp_impl.md), [`#[cgp_provider]`](cgp_provider.md), and [`#[cgp_fn]`](cgp_fn.md):
  write the providers the table names.
- [`DelegateComponent`](../traits/delegate_component.md) and
  [`IsProviderFor`](../traits/is_provider_for.md): the two traits each entry implements.
- [`RedirectLookup`](../providers/redirect_lookup.md): the provider behind `=>` and `open`.
- [`UseDelegate`](../providers/use_delegate.md): the legacy nested-table dispatch that `open`
  replaces; getters are commonly wired to [`UseField`](../providers/use_field.md).
- [`Path!`](path.md): the path syntax behind `@`-path keys and `=>` values.
- [`cgp_namespace!`](cgp_namespace.md): owns the `namespace` and `for` statements and reuses this
  macro's body grammar.

A table should be checked. Pair it with a standalone [`check_components!`](check_components.md), the
form larger codebases use because it can check generic keys, opened or namespaced wiring, and
individual provider layers. For basic wiring and while getting started,
[`delegate_and_check_components!`](delegate_and_check_components.md) wires and checks in one step so
the check cannot be forgotten. The fused macro accepts this whole grammar but derives checks only
from `:` and `->` mappings on single or list keys, so opened, redirected, and namespaced entries are
wired but left unchecked there. Plain `delegate_components!` without any check is right only for
[aggregate providers](../../concepts/aggregate-providers.md), which are providers rather than
contexts.

Two choices inside the table have a default. Prefer the `open` statement to the legacy nested
`UseDelegate` table for per-type dispatch. And move to a [namespace](cgp_namespace.md) once the same
wiring repeats across contexts, or once one table has grown too long to read; below that threshold
the namespace's extra hop costs more than it saves.
