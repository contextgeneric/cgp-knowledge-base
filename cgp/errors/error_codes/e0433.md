# E0433: use of an undeclared type, crate, or module

`E0433` is Rust's diagnostic for a path whose first segment names nothing in scope, so resolution
fails before the path can even be interpreted as a type.

## What it means

The compiler prints "cannot find type `Name` in this scope" with the label
``use of undeclared type `Name` `` under the caret, for a qualified path such as `Db::Row` as much
as for a bare type (checked on `rustc` 1.98.1 and the pinned nightly); an unresolved module or crate
reads "cannot find module or crate `name` in this scope" instead. It arises whenever a path's
leading segment is not bound by any item, import, or generic parameter visible at that point: a
misspelled type, a missing `use`, or a generic parameter that is not in scope where the path
appears. Where a similarly named item exists, `rustc` adds a `help:` suggesting it or the import
that would bring it in.

## The rule behind it

Rust resolves the first segment of a path in the scope surrounding the path, against the items,
imports, and generic parameters in effect there. A generic parameter is in scope only inside the
item that declares it, so a parameter declared on an `impl` is not visible in a `trait` the same
macro also generated, even though the two are emitted together: each item carries its own parameter
list, and there is no shared scope between them. This is ordinary path resolution as described in
the [Rust reference on paths](https://doc.rust-lang.org/reference/paths.html) and
[names and scopes](https://doc.rust-lang.org/reference/names/scopes.html); the code is a resolution
failure rather than a trait-solving one, which is why it is reported before any bound is evaluated
and why no obligation chain accompanies it.

`E0433` is distinguished from its neighbour [`E0425`](e0425.md) by *which* namespace resolution
failed in and how the compiler reached the name. A path used as a type or a qualifier resolves in
the type namespace and fails as `E0433` with the `use of undeclared type` label; a name the compiler
looked up without a path context (as it does for tokens inside a macro attribute's own arguments)
fails as `E0425` with the bare `not found in this scope` label. The headline text is identical in
both, so a grep for one will not find the other.

## Where CGP produces it

- [Out-of-scope generated name](../lowering/out-of-scope-generated-name.md): an
  [`#[impl_generics]`](../../reference/attributes/impl_generics.md) parameter named in the trait's
  own signature: the attribute scopes it to the generated impl, so the generated trait names a type
  not in its scope.
- The same class's [`Box` sibling](../lowering/out-of-scope-generated-name.md#a-third-sibling-box-in-a-no_std-crate):
  a `no_std` crate deriving `CgpVariant` over a variant with no fields without `Box` in scope, so
  the mutable extractor's bare `Box` resolves to nothing.
