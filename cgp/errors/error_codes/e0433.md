# E0433 — use of an undeclared type, crate, or module

`E0433` is Rust's diagnostic for a path whose first segment names nothing in scope, so resolution fails before the path can even be interpreted as a type.

## What it means

The compiler prints "failed to resolve: use of undeclared type `Name`" — rendered in the common single-segment case as "cannot find type `Name` in this scope" with the label `use of undeclared type` under the caret. It arises whenever a path's leading segment is not bound by any item, import, or generic parameter visible at that point: a misspelled type, a missing `use`, or a generic parameter that is not in scope where the path appears. Where a similarly named item exists, `rustc` adds a `help:` suggesting it or the import that would bring it in.

## The rule behind it

Rust resolves the first segment of a path in the scope surrounding the path, against the items, imports, and generic parameters in effect there. A generic parameter is in scope only inside the item that declares it, so a parameter declared on an `impl` is not visible in a `trait` the same macro also generated, even though the two are emitted together — each item carries its own parameter list, and there is no shared scope between them. This is ordinary path resolution as described in the [Rust reference on paths](https://doc.rust-lang.org/reference/paths.html) and [names and scopes](https://doc.rust-lang.org/reference/names/scopes.html); the code is a resolution failure rather than a trait-solving one, which is why it is reported before any bound is evaluated and why no obligation chain accompanies it.

`E0433` is distinguished from its neighbour [`E0425`](e0425.md) by *which* namespace resolution failed in and how the compiler reached the name. A path used as a type or a qualifier resolves in the type namespace and fails as `E0433` with the `use of undeclared type` label; a name the compiler looked up without a path context — as it does for tokens inside a macro attribute's own arguments — fails as `E0425` with the bare `not found in this scope` label. The headline text is identical in both, so a grep for one will not find the other.

## Where CGP produces it

- [Out-of-scope generated name](../lowering/out-of-scope-generated-name.md) — an [`#[impl_generics]`](../../reference/macros/cgp_fn.md) parameter named in the capability's own signature: the attribute scopes it to the generated impl, so the generated trait names a type not in its scope.
