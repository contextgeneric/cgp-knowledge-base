# E0404 — a trait was expected, but something else was found

`E0404` is Rust's diagnostic for a name used where a trait is required — a supertrait, a bound, or an `impl … for` header — that resolves to a type, a type parameter, or another non-trait item.

## What it means

The compiler prints "expected trait, found type parameter `Name`" (or "found struct", "found enum", "found type alias", according to what the name resolved to), with the caret on the name in the bound position and a `not a trait` label under it. When a trait of the same name is visible elsewhere, `rustc` adds a "you might have meant to refer to this trait" note pointing at it, and where the offending name is itself a declaration in view, a "found this type parameter" label under that declaration — so the diagnostic usually names both halves of the collision.

## The rule behind it

A bound position requires a path that resolves, in the type namespace, to a trait; resolution itself is name-based and namespace-based, not kind-directed, so the compiler resolves the name first and only then checks that what it found is a trait. A nearer binding therefore wins over a trait of the same name further out, and the mismatch surfaces as `E0404` rather than as a "no such trait" error. Inside a trait declaration an associated type's own name is such a nearer binding, which is why `type Foo: Foo;` resolves its bound to the associated type being declared rather than to a trait `Foo` in scope. This follows from the ordinary [name-resolution and shadowing rules](https://doc.rust-lang.org/reference/names/scopes.html) together with the [trait-bound grammar](https://doc.rust-lang.org/reference/trait-bounds.html); there is no RFC-level subtlety, only that a bound must name a trait and that resolution picks the closest binding.

## Where CGP produces it

- [Out-of-scope generated name](../lowering/out-of-scope-generated-name.md#a-sibling-the-shadowed-abstract-type) — its shadowed-abstract-type sibling: a [`#[cgp_type]`](../../reference/macros/cgp_type.md) trait declaring `type Database: Database` gives the abstract type the same name as the trait bounding it, so the bound resolves to the associated type, which the macro's expansion carries into a type-parameter position — hence "found type parameter".
