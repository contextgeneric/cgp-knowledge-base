# E0271 — a type mismatch resolving an associated-type projection

`E0271` is Rust's diagnostic for an associated type that resolves to something other than what a bound required — the trait itself is implemented, and only the projected type disagrees.

## What it means

The compiler prints "type mismatch resolving `<T as Trait>::Assoc == Expected`", followed by an "expected this to be `Expected`" note whose caret sits on whatever supplies the actual type, and a pair of `expected … found …` notes naming both types. It is the projection counterpart of [`E0277`](e0277.md): where `E0277` says a trait is not implemented at all, `E0271` says it *is* implemented but its associated type is not the one an equality constraint demanded. The distinction matters when reading a CGP failure, because it tells a reader the wiring exists and only its *type* choice is wrong.

## The rule behind it

An associated-type equality — written `Trait<Assoc = T>` in a bound, or arising from a projection the solver must unify — is a separate obligation from the trait bound it rides on. The solver first proves `T: Trait`, then normalizes `<T as Trait>::Assoc` and unifies the result with the required type; a failure of the second step is `E0271` while a failure of the first is `E0277`. The mechanism is the associated-type projection and equality-constraint machinery described in the [Rust reference on associated items](https://doc.rust-lang.org/reference/items/associated-items.html), with the bound syntax specified under [trait and lifetime bounds](https://doc.rust-lang.org/reference/trait-bounds.html); the surrounding inference rules trace to [RFC 195](https://rust-lang.github.io/rfcs/0195-associated-items.html), which introduced associated items and their equality constraints.

One consequence shapes every CGP instance: because the caret is placed on what supplies the *actual* type rather than on the bound that required it, the diagnostic points at a struct field or a `#[cgp_type]` declaration rather than at the wiring or the provider whose requirement was unmet.

## Where CGP produces it

- [Check-trait failure](../checks/check-trait-failure.md) — three faces of one mechanism. A context field whose name matches but whose type does not, so the `HasField` projection fails; the same where the *required* type is itself computed from an abstract type the context wires, so two of the context's own wiring decisions disagree; and an [abstract type](../../concepts/abstract-types.md) a provider pins with `#[use_type(Trait.{Assoc = T})]` while the context binds it to another type, where no field is involved at all.
