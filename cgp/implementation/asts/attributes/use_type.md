# `#[use_type]` — the AST stack

`#[use_type(HasErrorType.Error)]` imports an abstract associated type: it rewrites the bare alias (`Error`) everywhere in the host's signatures into its fully-qualified `<Self as HasErrorType>::Error` form, and adds the owning trait as a bound so those paths are well-formed. It is the richest of the attribute modifiers, with a small stack of AST types and a three-step transform driven off them; this page covers that stack and the shared collection mechanism lives in the [attribute-modifier overview](README.md). For the user-facing syntax and expansion, read the reference document [reference/attributes/use_type.md](../../../reference/attributes/use_type.md).

## The stack at a glance

An import parses into a `UseTypeAttribute` per spec, each carrying one or more `UseTypeIdent` entries, and the specs a host collects are held together in a `UseTypeAttributes`. Application then runs in three steps off `UseTypeAttributes`: **ground** each spec's own type positions, **substitute** every bare alias in one traversal with the `SubstituteAbstractTypes` visitor, and **add the bounds** to the trait or impl. The type-equality (`= T`) pins are derived separately by `derive_use_type_predicates`. The sections below follow the data through those types in order.

Two checks run before any of it, both in `type_predicates.rs`: `forbid_duplicate_aliases` rejects two imports resolving to one name, and `forbid_grounding_cycles` rejects an import list whose own positions resolve through each other. Together they establish the two properties the rest of the stack assumes — that an alias has exactly one owner, and that grounding terminates with every alias resolved.

## `UseTypeIdent`

`UseTypeIdent` is one imported associated type within a spec. It captures three pieces: the `type_ident` (the associated type's name, e.g. `Error`), an optional `as_alias` (the `as NewName` rename), and an optional `equals` (the `= ConcreteType` pin). Its `alias_ident()` returns the alias when one is written and the type identifier otherwise — this is the name that appears bare in the host's signatures and that the substitution matches against. Parsing reads the identifier, then optionally `as <ident>`, then optionally `= <type>`, so the grammar is `Ident (as Ident)? (= Type)?`.

## `UseTypeAttribute`

`UseTypeAttribute` is one import spec — a trait path, the types imported from it, and the context they are projected against. It holds a `context_type` (the type whose associated type is imported, defaulting to `Self` or set by a trailing `in Context`), the `trait_path` (a `PathWithTypeArgs`, so the owning trait may be a full path or carry generic arguments such as `HasFooType<X>`), and a `Vec<UseTypeIdent>` of the types imported from that trait.

Its parser is where the `.`-versus-`::` separation is decided. It parses the trait path, consumes a `.`, and reads either a single `UseTypeIdent` or a brace-delimited comma list of them (`HasTypes.{A, B as C}`); it then reads an optional `in Context` suffix, parsing `Context` as a `PathWithTypeArgs`, with no suffix defaulting the context to `Self`. The `.` — not `::` — is what separates the trait from the associated type, so a trait that is itself a path keeps its `::` inside `trait_path` while the `.` unambiguously marks where the associated type begins; the `in` keyword, reserved in Rust, marks the context clause just as cleanly since it can never appear inside a type or path:

```rust
// #[use_type(foo::bar::HasScalarType.Scalar in Context)]
//            └────trait_path────┘ └assoc┘    └─ctx─┘
```

`UseTypeAttribute` also carries `replace_ident`, the per-spec lookup the substitution visitor calls: given an identifier, it returns the fully-qualified replacement identifier if the identifier matches one of the spec's `alias_ident()`s, and — importantly — **stamps the user's original span onto the replacement**. Preserving the span is what makes a caret on a mistyped imported type point at the identifier the user wrote rather than at the whole macro block.

Its third pair of methods, `groundable_types` and `groundable_types_mut`, names the spec's own type positions that *grounding* resolves: the `context_type`, and the type arguments of the `trait_path`. Both end up inside the emitted `<Context as Trait<Args…>>::Assoc` path, so an alias left bare in either resolves to nothing — which is why the set is one notion rather than two. Naming it on the spec keeps the three things that walk it in agreement: the grounding pass that rewrites those positions, the bounds derived from them, and the cycle check that reads dependency edges out of them. A lifetime or const argument is skipped, since neither can name an abstract type.

## `UseTypeAttributes` and the three-step transform

`UseTypeAttributes` holds the `Vec<UseTypeAttribute>` a host collected and owns the transform that applies them. It exposes two entry points — `transform_item_trait` for a generated trait and `transform_item_impl` for a generated impl — and both run the same three steps, differing only in the bounds they add at the end. Each returns early when there are no specs, then calls `forbid_duplicate_aliases` and `forbid_grounding_cycles` before transforming anything.

**Step one — grounding.** `grounded_specs` resolves each spec's [groundable positions](#usetypeattribute) up front so the later steps agree on one fully-qualified context and one fully-qualified trait path. An `in Context` whose `Context` is itself imported by another spec — as in `HasTypes.Types, HasScalarType.Scalar in Types` — is rewritten from the bare alias `Types` into `<Self as HasTypes>::Types`, and a trait argument naming an alias is grounded identically, so `HasDbType.Db, HasPoolType<Db>.Pool` projects against `HasPoolType<<Self as HasDbType>::Db>`. A position naming a real generic parameter or `Self` is left alone. The pass iterates to a fixpoint, running the substitution visitor over each spec's groundable positions and stopping when a pass makes no change; because each pass grounds one more level, `attributes.len()` passes cover any acyclic graph over that many specs (so `HasA.A, HasB.B in A, HasC.C in B` grounds `B` to `<<Self as HasA>::A as HasB>::B`). Every graph that reaches here is acyclic, because `forbid_grounding_cycles` has already rejected the rest.

**Step two — substitution.** A single `SubstituteAbstractTypes` traversal, holding *every* grounded spec at once, rewrites each bare use of an alias into its fully-qualified associated type:

```rust
// #[use_type(HasErrorType.Error)]  turns a bare `Error` into:
<Self as HasErrorType>::Error
```

Grounding the contexts up front is what lets one pass suffice: the replacement a spec emits already contains no bare alias, so the visitor never revisits its own output, and because aliases are unique (guaranteed by `forbid_duplicate_aliases`) the order among specs is irrelevant. The visitor's matching rules are covered under [SubstituteAbstractTypes](#substituteabstracttypes) below.

**Step three — adding the bounds.** This is where the two entry points diverge:

- `transform_item_trait` pushes each `Self`-context spec's trait path onto the consumer trait's *supertraits*, so the abstract type is available to every signature. For a foreign `in Context` spec it instead adds a plain `Context: Trait` predicate to the trait's `where` clause, so the substituted `<Context as Trait>::Assoc` signatures are well-formed without the author declaring the bound. The type-equality (`= T`) form is an impl-side pin and is deliberately *not* added to a trait here.
- `transform_item_impl` derives the impl-side `where` predicates through `derive_use_type_predicates` and extends the impl's `where` clause with them. These carry the `= T` equality pins as associated-type bindings; the pins are impl-side only and never reach the trait.

## `derive_use_type_predicates` and the equality pins

`derive_use_type_predicates` (in `type_predicates.rs`) turns a set of grounded specs into the impl-side `where` predicates they contribute — one `context_type: trait_path` bound per spec, carrying any `= T` pins as associated-type bindings inside the trait path (`Context: Trait<Assoc = T>`). It reads each spec's already-grounded positions directly rather than re-resolving aliases, which is why grounding must run first.

The pins are merged **into** the trait path's own argument list rather than appended as a second angle-bracketed group, which matters as soon as the imported trait is generic. A pin on `HasFooType<u8>` has to render as `HasFooType<u8, Foo = u32>`, because `HasFooType<u8><Foo = u32>` is not a trait bound in any position — so the predicate is built from the path's *head* followed by one list holding the existing arguments and then the bindings, instead of from the `PathWithTypeArgs` whole (which renders its arguments as a trailing group). Emitting the two groups separately failed inside the macro with a bare "failed to parse internal tokens to type `syn::generics::WherePredicate`" naming no cause, since the malformed tokens never reached the compiler.

The pins can also **unify two imported abstract types**, and they do it by the same substitution the rest of the attribute uses rather than by a special case. `find_type_equality` runs `SubstituteAbstractTypes` over the pin's right-hand side, so an imported alias is grounded *wherever it occurs inside it*: `HasHashedPasswordType.{HashedPassword = Password}` grounds a right-hand side that *is* an alias into `<Self as HasPasswordType>::Password`, and `HasTransactionType.{Transaction = Tx<Db>}` grounds one *nested in a generic argument* into `Tx<<Self as HasDbType>::Db>`, as does an alias inside a qualified path (`<Db as Database>::Transaction`). A right-hand side naming no alias is used as written. Treating the target as an ordinary type is what makes the two shapes one rule; comparing the whole type for equality — as an earlier implementation did — grounded only the first and passed a nested alias through as a bare identifier that resolved to nothing.

The one exclusion is the pinned alias itself: `specs_excluding_alias` drops it from the substitution set for its own pin, so a degenerate self-pin (`{Foo = Foo}`) stays an unresolved-name error rather than silently becoming a vacuous `Self: HasFooType<Foo = <Self as HasFooType>::Foo>` bound.

The module also holds the two validation functions the transform runs before anything else, the simpler of which is `forbid_duplicate_aliases` (the other has its own section below). It rejects any two imports that resolve to the same identifier or alias: it flattens every `UseTypeIdent` across all specs into one list and compares every pair by `alias_ident()`, so the check catches a collision across separate specs *and* within a single braced list, uniformly for components, impls, and functions. A shared alias would make the substitution silently pick the first match and drop the rest, so it must be an error.

## `forbid_grounding_cycles`

`forbid_grounding_cycles` (also in `type_predicates.rs`) rejects an import list whose groundable positions resolve through one another in a cycle, the one arrangement for which no grounding order exists. Grounding resolves every spec against every other and iterates, which is what makes the *order* of nested imports irrelevant — `HasC.C in B, HasB.B in A, HasA.A` grounds exactly like the front-to-back spelling. A cycle asks for each position to be resolved before the other, so `#[use_type(HasA.A in B, HasB.B in A)]` has no order at all — nor does a loop running through a trait argument (`#[use_type(HasPoolType<Pool>.Pool)]`), nor the one-node context case `#[use_type(HasAType.A in A)]`.

The check builds a dependency graph over the specs and searches it depth-first. Each spec's groundable positions are walked with [`collect_bare_aliases`](https://github.com/contextgeneric/cgp/blob/main/crates/macros/cgp-macro-core/src/visitors/collect_bare_aliases.rs), and every collected identifier that another spec imports becomes an edge to that spec, labelled with the referencing token. A back edge into a spec still on the search path is a cycle, reported on the token that closes the loop and worded with the aliases along it (`` `B` -> `A` -> `B` ``, or `` `A` -> `A` `` for a self-reference). Because the collector and the substitution visitor share [`bare_alias_ident`](#substituteabstracttypes), a position the substitution would rewrite is always a position the check can see — the two cannot disagree about what counts as a reference.

**The check has to run before grounding, because the obvious after-the-fact test does not work.** Grounding does not leave a cyclic alias bare: each pass substitutes against the *previous* pass's snapshot, in which the other context is itself still ungrounded, so every pass wraps one more layer and the alias ends up buried at the innermost position of a deep projection. The two-spec cycle above once reached the compiler as

```rust
pub trait Deep
where
    <<<A as HasB>::B as HasA>::A as HasB>::B: HasA,
    <<<B as HasA>::A as HasB>::B as HasA>::A: HasB,
{
    fn deep(&self) -> <<<<A as HasB>::B as HasA>::A as HasB>::B as HasA>::A;
}
```

with the bare `A` and `B` surviving only four levels down, which is where the compiler's `E0425` caret landed. Asking whether a context is "still a bare alias" after grounding therefore finds nothing, and the depth of the spiral grows with the number of specs. The spec graph states the problem directly instead.

## `SubstituteAbstractTypes`

`SubstituteAbstractTypes` (in [visitors/substitute_abstract_type.rs](https://github.com/contextgeneric/cgp/blob/main/crates/macros/cgp-macro-core/src/visitors/substitute_abstract_type.rs)) is the `VisitMut` that performs the bare-alias rewrite in a single traversal. Holding every spec at once — rather than running one visitor per spec — is what lets one pass over the item handle all imports regardless of the order they were written. It rewrites a type only when the type is a **bare alias reference** whose identifier matches a spec's `alias_ident()`, replacing it with `<context_type as trait_path>::replacement_ident` and recording `is_changed`. `is_changed` is what the grounding fixpoint reads to decide whether a further pass would be a no-op.

What counts as a bare alias reference is decided by one shared function, `bare_alias_ident`, which reports the identifier of an unqualified, single-segment, argument-free type path (`qself: None`, no leading colon, one segment, `PathArguments::None`) and `None` for anything else. The strictness is deliberate: a path that already carries a qualifier, arguments, or more than one segment is not a bare alias and is left untouched, so a genuine `Self::Error` or the head of a generic `Foo<Error>` is not disturbed. Factoring the guard out of the visitor rather than inlining it is what lets [`forbid_grounding_cycles`](#forbid_grounding_cycles) follow exactly the references the substitution would rewrite, through the read-only `CollectBareAliases` counterpart that shares it.

## Behavior and corner cases

**A `=` equality is rejected outright on `#[cgp_component]`.** `CgpComponentAttributes::parse` scans each imported `UseTypeIdent` for an `equals` and returns a spanned "Type equality constraints cannot be used in component trait definition" error, because a component *definition* cannot pin an abstract type to a concrete one — the pin belongs on an impl. The impl and function collectors accept the equality form.

**A foreign `in Context` bound reaches the trait.** On a component or function trait, `transform_item_trait` adds the `Context: Trait` predicate to the trait's `where` clause for a foreign spec. Without this the constraint would be silently dropped, leaving a signature that only compiles when the author happens to supply the bound elsewhere; adding it is what makes the substituted `<Context as Trait>::Assoc` paths well-formed by construction.

**The rewrite reaches type positions and expression-path qualifiers.** `SubstituteAbstractTypes` implements two visits. `visit_type_mut` rewrites an alias wherever a `syn::Type` occurs — a signature, a `where` predicate, a `let` annotation, an implicit-argument annotation, a pin's right-hand side — and `visit_expr_path_mut` rewrites an alias that *qualifies* an expression path, so `Transaction::begin_from(pool)` becomes `<<Self as HasTransactionType>::Transaction>::begin_from(pool)` (a qualified-type path, since `<Self as Trait>::Assoc::method` is not valid syntax). Covering both is what makes the alias mean one thing throughout the item: an alias that worked in a `let` annotation but not as the qualifier of the call on the next line was an inconsistency, not a boundary — the author claims the name by importing it, and `forbid_duplicate_aliases` guarantees nothing else in the import list claims it too.

**The boundary that remains is arity.** Only an expression path of *two or more* segments is rewritten. A multi-segment `Transaction::foo` can only mean an associated item of the type, while a bare single-segment `Transaction` in expression position names a **value** — a unit struct or an enum variant — which an abstract type can never be, so it is left alone. That keeps the one genuinely ambiguous case out of the rewrite: an alias may share a name with a unit struct the body constructs, and the arity test tells the two apart without guessing.

**Nested-import order does not matter, and an arrangement with no order is rejected.** Grounding runs a fixpoint over *all* specs at once, so a spec's `in Context` may name an alias imported by any other spec regardless of where it sits in the list — `HasC.C in B, HasB.B in A, HasA.A` grounds exactly like the front-to-back `HasA.A, HasB.B in A, HasC.C in B`. A shared context is equally fine: `HasA.A, HasB.B in A, HasC.C in A` is a diamond rather than a chain, and both dependents pick up the one grounded `A`. The only arrangement with no valid order is a cycle, which [`forbid_grounding_cycles`](#forbid_grounding_cycles) rejects at macro time with a spanned error.

**Grounding deliberately stops at the trait path's *head*.** It reaches the context and the trait's generic arguments, but not the trait name itself, so `#[use_type(HasFooType.Foo, Foo.Bar)]` leaves the second spec's `Foo` alone. This is not the missing third case the adjacency test would call for, because the head is the one position where an alias can never be meant: it must name a **trait**, and an alias names a **type**. Grounding it would turn a plain trait-resolution error on the token the user wrote — `E0405` "cannot find trait `Foo`", with the caret on that `Foo` — into the unparseable `<Self as <Self as HasFooType>::Foo>::Bar`, making a clear error worse. The check keeps the same boundary — the head is not among the spec's [groundable positions](#usetypeattribute) — so a trait path that happens to match an alias raises no false cycle either.

**A circular type-equality pin is lowered faithfully, unlike a circular context.** Two pins naming each other — `#[use_type(HasFooType.{Foo = Bar}, HasBarType.{Bar = Foo})]` — emit `Self: HasFooType<Foo = <Self as HasBarType>::Bar>` alongside `Self: HasBarType<Bar = <Self as HasFooType>::Foo>`, and the compiler answers with `E0275` "overflow evaluating the requirement". That is deliberately *not* treated as the pin-side analogue of a context cycle, because the two differ in kind. A context cycle has no grounding order, so the macro cannot produce well-formed output at all; a pair of circular pins grounds in one pass and produces output whose meaning is perfectly well defined — it asserts that two abstract types are equal, which some context may well satisfy. What fails is the solver's ability to discharge the assertion, and whether a bound is dischargeable is exactly the information a macro cannot obtain at expansion time. Rejecting it would refuse a meaningful constraint on the strength of a guess, so the pin is emitted and the compiler decides.

- [use_type_fn_expr_path.rs](https://github.com/contextgeneric/cgp/blob/main/crates/tests/cgp-tests/tests/abstract_types/use_type_fn_expr_path.rs) covers the expression-path rewrite and its arity boundary: an alias qualifying an associated-function call and an associated-const read are both rewritten to the qualified-type form (with a `let` annotation in the same body pinning that the type-position rewrite still works alongside), while a bare single-segment alias naming a unit struct in expression position is left as the value it is.

- [use_type_fn_shared_context.rs](https://github.com/contextgeneric/cgp/blob/main/crates/tests/cgp-tests/tests/abstract_types/use_type_fn_shared_context.rs) pins a diamond in the grounding graph — two imports naming one alias as their context — which is the acyclic shape the cycle check must not mistake for a cycle.

The rejection cases are pinned in [parser_rejections/use_type.rs](https://github.com/contextgeneric/cgp/blob/main/crates/tests/cgp-macro-tests/tests/parser_rejections/use_type.rs): a `=` equality on a component; a duplicate identifier or alias across specs, within one braced list, and on a component; and five grounding cycles — a self-referential context, a two-spec cycle, a three-spec cycle (which a check comparing only adjacent pairs would miss), a cycle running through a trait argument rather than an `in` clause, and a cycle on a component trait rather than a function.
