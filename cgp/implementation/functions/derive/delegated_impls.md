# Delegated-impl synthesis

The delegated-impl functions turn a trait's items into the body of an impl that forwards every method, associated type, and constant to a chosen delegate type. They are the shared machinery behind the forwarding impls that `#[cgp_component]` and `#[derive_delegate]` emit, so the forwarding shape is written once and reused by every impl that routes a trait through another type.

Each caller supplies the delegate type, and each generated item calls the delegate's version of the trait item. A method `fn area(context: &Context) -> f64` gets the body `<delegate>::area(context)`, with `.await` appended when the signature is `async`. An associated type becomes `type Output = <delegate as Trait>::Output;`, and an associated const becomes `const N: usize = <delegate as Trait>::N;`. The callers differ only in which type fills `<delegate>` and which trait qualifies the projections.

## Callers

Five impls use these functions, split by whether they forward a trait to itself or across traits:

- The **provider blanket impl** and the **`RedirectLookup` impl** implement the provider trait by forwarding to another implementation of the same provider trait, so they call `provider_trait_to_impl_items`, which qualifies projections through the provider trait.
- The **consumer blanket impl** forwards the consumer trait to the provider trait, and the **`UseContext` impl** forwards the provider trait to the consumer trait. Both cross traits, so they call `trait_items_to_delegated_impl_items` with the *other* trait's path.
- The **`UseDelegate` impl** generated by [`#[derive_delegate]`](../../asts/attributes/derive_delegate.md) forwards the provider trait to the delegate a table selects, through `trait_items_to_delegated_impl_items`.

The callers are documented in [entrypoints/cgp_component.md](../../entrypoints/cgp_component.md) and the [cgp_component AST stack](../../asts/cgp_component.md).

## `trait_items_to_delegated_impl_items`

`trait_items_to_delegated_impl_items` maps a slice of `syn::TraitItem` to the `Vec<syn::ImplItem>` that forwards each one, taking the trait items, the `delegate_type`, and the `provider_trait_path` that qualifies associated-type and const projections. It applies `trait_item_to_delegated_impl_items` to each item, which handles three kinds:

- A **function** is forwarded by `signature_to_delegated_impl_item_fn`, which keeps the signature, drops the method's attributes, and builds the call from each parameter's name (`self` for the receiver).
- An **associated type** becomes `type Name<generics> = <delegate as provider_trait_path>::Name<generics>;`, built by `trait_to_impl_item_type`, which keeps the item's attributes.
- An **associated const** becomes `const Name<generics>: Ty = <delegate as provider_trait_path>::Name<generics>;`, keeping the const's type and attributes.

Any other trait item, such as a macro invocation, fails with a spanned `unsupported trait item: …` error that prints the item's debug form, so the macro fails rather than dropping the item.

## `provider_trait_to_impl_items`

`provider_trait_to_impl_items` is the wrapper for forwarding a provider trait to itself. It takes the provider `ItemTrait` and a `delegate_type`, rebuilds the trait path from the trait's identifier and type generics (through `split_for_impl`), and calls `trait_items_to_delegated_impl_items` with that path.

## Behavior and corner cases

The projections are qualified through the supplied trait path rather than the impl's own trait, which matters when the two differ. When the consumer blanket impl forwards to the provider trait, an associated type is projected as `<… as ProviderTrait>::Output`, because the value lives on the provider side. Method forwarding needs no qualification: it calls `<delegate>::method(args)` and relies on the impl's `where` clause to bring the delegate's trait into scope.

## Known issues

`signature_to_delegated_impl_item_fn` names each argument by parsing the parameter's pattern as an `Ident`, so a parameter that is not a plain identifier cannot be forwarded. A `_` parameter, which Rust allows in a bodiless trait method, and a destructuring pattern such as `(a, b): (u32, u32)` in a default method both fail with `expected identifier`, followed by ``failed to parse internal tokens to type `proc_macro2::Ident` ``. The correct behavior is to bind such a parameter to a fresh name (a reserved `__arg_N__`, say) in the generated signature and call. Every caller shares the defect; the user-visible side is in [reference/macros/cgp_component.md](../../../reference/macros/cgp_component.md#known-issues).

## Tests

These functions have no dedicated unit test; they are covered through the `#[cgp_component]` expansion snapshots, which pin the forwarding bodies.

- The plain case in [basic_delegation/component_macro.rs](https://github.com/contextgeneric/cgp/blob/main/crates/tests/cgp-tests/tests/basic_delegation/component_macro.rs) shows method forwarding through the consumer and provider blanket impls and through `UseContext` and `RedirectLookup`.
- The default-method case in [basic_delegation/default_methods.rs](https://github.com/contextgeneric/cgp/blob/main/crates/tests/cgp-tests/tests/basic_delegation/default_methods.rs) confirms a forwarded call resolves to a default body.
- Associated-type forwarding is pinned by the `#[cgp_type]` snapshots in the `abstract_types` target.
- [basic_delegation/component_assoc_const.rs](https://github.com/contextgeneric/cgp/blob/main/crates/tests/cgp-tests/tests/basic_delegation/component_assoc_const.rs) pins associated-const forwarding in all four impls and reads the const through wiring.
- [async_and_send/component_async.rs](https://github.com/contextgeneric/cgp/blob/main/crates/tests/cgp-tests/tests/async_and_send/component_async.rs) pins `.await` forwarding for an `async` method.
- No test pins the parameter-pattern defect under Known issues.

## Source

- The functions live in [cgp-macro-core/src/functions/delegated_impls/](https://github.com/contextgeneric/cgp/tree/main/crates/macros/cgp-macro-core/src/functions/delegated_impls/):
